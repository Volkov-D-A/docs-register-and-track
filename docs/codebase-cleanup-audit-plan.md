# План аудита кодовой базы на неактуальные части

Дата: 24 сентября 2026 года  
Статус: план принят; этапы 0–1 завершены, этапы 2–8 выполняются.
Ход работ и реестр находок: [codebase-cleanup-audit.md](codebase-cleanup-audit.md).

## Цель и результат

Найти код, данные, контракты, тесты, зависимости и инфраструктуру, которые
больше не обслуживают поддерживаемые сценарии Docflow. По каждому кандидату
получить проверяемое основание для сохранения, исправления или удаления.
Итогом аудита должны стать реестр находок, карта действующих контрактов,
небольшие задачи на удаление и обновлённые тесты и документация. Само наличие
старого имени, отсутствия прямых ссылок или низкого покрытия не доказывает,
что часть проекта не нужна.

Текущая архитектурная граница: React → generated Wails bindings →
`internal/desktop/services` → `internal/desktop/serverclient` → HTTP API
`docflow-server` → `internal/server/services` → repository, PostgreSQL,
SeaweedFS и outbox. Вторые точки входа: запуск, фоновые задачи, SSE,
резервирование, миграции, CLI, сборка и эксплуатационные скрипты.

### Реестр находок

Для каждого кандидата записывать:

| Поле | Содержание |
| --- | --- |
| ID, место | Файл, символ или контракт, диапазон строк, владелец подсистемы |
| Тип | Мёртвый код, лишние данные, совместимость, дублирование, тест, зависимость, артефакт, документация |
| Доказательство | Поиск вызовов и регистраций, трасса данных, сценарий, история Git, тест или наблюдение |
| Внешние потребители | Desktop, сервер, БД, опубликованные сборки, операционные скрипты, сторонние клиенты |
| Риск удаления | Пользовательские данные, права, безопасность, миграции, форматы backup, rollback, Linux/Windows |
| Решение | Удалить, упростить, исправить контракт, оставить с обоснованием, требуется решение владельца |
| Проверка | Минимальная проверка изменения и результат |
| Статус | Кандидат → подтверждён → исправлен или обоснованно оставлен |

Вести также числовую сводку: кандидаты, подтверждённые находки, закрытые
находки, удалённые файлы/строки/зависимости и оставшиеся исключения. Размер
diff сам по себе не является критерием качества.

## Этап 0. Зафиксировать границы и исходное состояние

1. Записать commit, состояние рабочего дерева, поддерживаемые версии desktop и
   сервера, способ обновления развёрнутых экземпляров, целевые ОС и действующие
   форматы данных. Сверить `README.md`, `docs/tech_docs.md`, `go.mod`,
   `frontend/package.json`, `Makefile`, Compose и release gate с кодом.
2. Установить, какие внешние клиенты HTTP API реально поддерживаются и какие
   версии могут одновременно работать при обновлении. До этого не считать
   маршрут или поле избыточным лишь потому, что его не вызывает текущий desktop.
3. Отметить защищённые контракты: версии миграций и сохранённые БД, backup и
   restore, audit и журнал документов, права доступа, idempotency, имена
   событий, конфигурацию развёртывания и опубликованные Wails методы.
4. Составить таблицу доступных точечных проверок. Базовый полный прогон здесь
   не нужен: для каждой будущей правки выбирать тест по конкретному риску.

**Выход:** согласованная область аудита и список контрактов, требующих
проверки использования за пределами исходников.

## Этап 1. Инвентаризировать все исполняемые части

1. Снять перечень исходников, тестов, SQL-миграций, скриптов, ресурсов,
   сгенерированных файлов и зависимостей. Разделить исходники, generated code
   (`frontend/wailsjs`, release assets), временные результаты (`dist`,
   `.test-build`, бинарники) и файлы, которые обязаны попадать в сборку.
2. Зафиксировать точки входа: `main.go`, `cmd/docflow-server`, команды `tools`,
   Wails `Bind`, HTTP route registration, SSE, background lifecycle, outbox
   handlers, `go:generate`, Vite entry, lazy imports, Makefile, Dockerfile и
   Compose. Проверить варианты Linux/Windows и build tags.
3. Построить карту пакетов и зависимостей. Проверить архитектурные границы:
   desktop не зависит от `internal/server`; сервер не зависит от
   `internal/desktop` и Wails; shared-пакеты независимы от обеих сторон.
4. Составить кандидатов из статического поиска: неиспользуемые экспорты и
   импорты, файлы без достижимого entrypoint, неиспользуемые npm/Go зависимости,
   пустые интерфейсы/адаптеры и дубли. Любой результат перепроверить с учётом
   reflection, сериализации, Wails bindings, HTTP registration, SQL и скриптов.

**Выход:** карта точек входа и первичный реестр кандидатов с пометкой о
непроверенных динамических потребителях.

## Этап 2. Проследить пользовательские сценарии сквозь все слои

1. Взять матрицу сценариев: запуск и bootstrap, login/logout, четыре вида
   документов, поиск и карточки, регистрация и изменение, поручения,
   ознакомления, связи, вложения, справочники, права, статистика, настройки,
   миграции, backup/restore, аудит, уведомления и ошибки обслуживания.
   Проверить роли и ограниченные права, а не только администратора.
2. Для каждого действия построить прямую цепочку: экран/компонент → вызов
   Wails → desktop service → HTTP client → маршрут → server service → port →
   repository/storage/outbox. Затем обратную: результат → DTO/JSON →
   frontend state → реально отображаемое поле, решение или side effect.
3. Сопоставить опубликованные Wails методы с `frontend/wailsjs`, импортами
   frontend и `internal/desktop/app/testdata/wails-api.json`. Сопоставить
   HTTP-маршруты с вызовами `serverclient` и подтверждёнными внешними
   потребителями. Выделить однонаправленные цепочки без потребителя.
4. Проверить отдельно операции, живущие без открытого экрана: SSE resync,
   outbox, планировщик backup, telemetry, startup/maintenance и shutdown.

**Выход:** матрица «сценарий → цепочка → владелец → проверка», список
неиспользуемых ветвей с доказательством или открытым вопросом.

## Этап 3. Аудировать движение и форму данных

1. Для каждого запроса и ответа проследить поля через модели, DTO, JSON,
   Wails и TypeScript: где значение вычисляется, передаётся, сохраняется,
   читается, отображается или влияет на решение. Особо искать поля, которые
   дорого получают на сервере, но не отправляют, и поля, которые отправляют,
   но frontend никогда не использует.
2. Проследить данные из SQL `SELECT` до `Scan`, mapping и ответа. Проверить
   лишние joins, count, поля карточки в списках, повторные запросы и
   вычисления, результаты которых сразу отбрасываются. Не удалять данные,
   нужные проверке прав, журналированию или побочным эффектам.
3. Проследить входные поля от формы до handler/repository. Найти поля,
   принимаемые, но игнорируемые; значения по умолчанию, скрывающие потерю
   данных; разные имена одного поля; структуры, используемые лишь частично.
4. Проверить SSE и outbox payload: producer → запись/публикация → consumer →
   действие UI/worker. Отдельно рассмотреть неиспользуемые типы событий,
   лишние поля и бесхозные ветки retry. Для telemetry проверить, что сведения
   проходят desktop buffer, API и серверный logging pipeline.
5. Зафиксировать необходимость каждого поля публичного ответа до сокращения:
   действующие внешние клиенты, сохранённые файлы, старые desktop-сборки и
   документированный контракт могут требовать переходного периода.

**Выход:** таблица полей и событий «источник → потребитель → действие»,
подтверждённые потери и избыточные передачи данных.

## Этап 4. Проверить наследие и код совместимости

1. Найти прежние имена, алиасы, fallback, преобразования старых форматов,
   двойные пути выполнения, version checks и устаревшие параметры в Go,
   TypeScript, SQL, конфигурации и документации. Поиск по `legacy`,
   `deprecated`, `compat`, `fallback` и старым именам даёт кандидатов, а не
   решение об удалении.
2. Для каждого случая установить источник появления, последнюю версию,
   которая его использовала, и реальную политику обновления. Проверить
   сохранённые пользовательские настройки, БД, backup-архивы и старые
   установленные desktop-сборки.
3. Отделить обязательную совместимость от исторического слоя. В частности,
   проверить `page`/`cursor` контракт списков, короткие UI-ключи видов
   документов, UX profile labels и поведение при несовпадении сборок. Не
   трактовать защищающие проверки версии как «legacy» без подтверждения.
4. Для подтверждённо ненужного слоя описать последовательность: удалить
   producer и consumer, затем DTO/адаптер, тесты, конфигурацию и документацию.
   Если требуется переход, записать срок и критерий завершения перехода.

**Выход:** реестр переходных слоёв с датой или условием удаления; сохранённые
слои имеют конкретную причину, а не бессрочное «на всякий случай».

## Этап 5. Проверить хранилище и операционный контур

1. Сопоставить таблицы, колонки, индексы и ограничения миграций 001–012 с
   живыми SQL-запросами, записью событий и действующими сценариями.
   Проверить данные, которые создаются, но больше нигде не читаются, а также
   table/column, используемые только тестами. Исторические миграции не
   переписывать: изменение существующей БД требует отдельной миграции и
   плана rollback.
2. Проверить lifecycle вложения: upload, metadata, выдача файла, delete,
   compensation, reconciliation и outbox. Для backup/restore отдельно
   проверить форматы архивов, каталог, staging, SMB и восстановление.
3. Сопоставить env/config ключи, Compose services, health checks, Dockerfile,
   скрипты, цели Makefile и release gate с текущим deploy flow. Проверить
   случайно сохранённые генерируемые результаты и локальные артефакты;
   подтверждать их удаление через правила сборки и `.gitignore`.
4. Проверить отключённые флаги и альтернативные реализации, но учитывать
   аварийное восстановление и maintenance: редкий вызов не означает
   неиспользуемый код.

**Выход:** список неактуальных элементов схемы и окружения, для каждого —
план безопасного удаления и влияние на существующие установки.

## Этап 6. Аудировать тесты и тестовую инфраструктуру

1. Сопоставить каждый существенный тест с текущим публичным поведением и
   риском регрессии. Выявить ожидания старых методов, прежних DTO, кодов
   ошибок, маршрутов и SQL-деталей; проверить, не закрепляют ли они уже
   удалённый путь вместо актуального пользовательского сценария.
2. Проверить `internal/server/mocks`, `internal/server/testutil`,
   `frontend/test/componentTestUtils.tsx`, Wails mock, fixtures, тестовые
   Compose-стеки и скрипты. Для каждого helper/fixture найти вызывающий тест,
   сравнить mock с действующим интерфейсом и проверить, не маскирует ли он
   пропущенное поле или вызов. Удалять вместе с последним потребителем.
3. Отметить тесты, которые повторяют реализацию, проверяют недостижимую ветку
   или слепо сверяют большой snapshot. Заменять их тестом наблюдаемого
   поведения там, где риск реален; не увеличивать набор только ради покрытия.
4. Проверить контрактные тесты Wails/HTTP и узкие интеграционные сценарии,
   необходимые для прав, транзакций, миграций и хранения файлов. Их низкая
   частота запуска не является основанием для удаления.

**Выход:** перечень тестов и фикстур на удаление/переписывание, а также
пробелов в защите действующих контрактов.

## Этап 7. Свести находки и расставить приоритеты

1. Убрать дубликаты реестра и сгруппировать находки по цепочкам причин:
   например, неиспользуемый экран → Wails метод → HTTP маршрут → DTO → mock.
   Удалять целую цепочку, чтобы не оставить висячие адаптеры.
2. Оценить для каждой группы уверенность и риск. Сначала делать локальные
   удаления без внешнего контракта, затем внутренние цепочки; публичные API,
   данные БД, backup и deploy требуют доказательства совместимости и
   отдельной задачи.
3. Сформировать небольшие независимые изменения с конкретными файлами,
   ожидаемым поведением и точечной проверкой. Отдельно перечислить случаи,
   где решение зависит от фактов о развёрнутых версиях или внешних клиентах.

**Выход:** упорядоченный backlog, который можно выполнять и проверять
поэтапно, без большого труднообозримого удаления.

## Этап 8. Удалять подтверждённое и проверять результат

1. В каждом изменении сначала зафиксировать действующий сценарий и
   доказательство неиспользования. Удалить код, тестовые заглушки,
   неиспользуемые DTO/типы, зависимости и конфигурацию в пределах одной
   связанной цепочки. Обновить `README.md`/`docs/tech_docs.md`, если контракт
   или эксплуатация изменились.
2. Использовать минимальную достаточную проверку: просмотр diff для
   документации; затронутый Go-пакет или frontend test для поведения;
   интеграционный стек из `testing/compose/integration.yaml` для SQL,
   транзакций, миграций и SeaweedFS, когда без него риск не проверить.
   Перед тяжёлой проверкой записать, какой риск она закрывает.
3. При изменении Wails API генерировать bindings обычным `make dev-client`
   или сборкой `make build-linux`/`make build-windows` и проверить diff
   `frontend/wailsjs`. Generated files вручную не редактировать. При
   изменении зависимостей Go выполнить `go mod tidy` и проверить `go.mod` и
   `go.sum`; для frontend проверить lockfile и нужную сборку.
4. После каждого изменения сверить реестр: нет ли оставшихся вызовов,
   фикстур, маршрутов, текстов документации и осиротевших тестов. Если
   подтверждение не удалось получить, оставить код и зафиксировать причину.

**Выход:** небольшие проверенные изменения, связанные с находками реестра.

## Этап 9. Закрыть аудит и закрепить результат

1. Повторно пройти карту entrypoints, контрактов и потоков данных на
   оставшиеся однонаправленные цепочки. Убедиться, что каждая открытая находка
   либо имеет владельца и условие решения, либо закрыта доказательством.
2. Проверить актуальность документации, `Makefile`, release gate и тестовых
   стендов. Полный release gate запускать при подготовке релиза или когда
   совокупность изменений выходит за охват точечных проверок.
3. Подготовить итог: что удалено, что оставлено и почему, какие внешние
   сведения всё ещё нужны, какие риски проверены тестами, как изменились
   объём кода и зависимости. Сохранить способ повторения аудита при
   следующем крупном изменении архитектуры.

**Критерий завершения:** у всех обнаруженных кандидатов есть решение и
доказательство; подтверждённые лишние цепочки удалены целиком; контракты,
миграции и поддерживаемые сценарии остаются согласованными; оставшиеся
исключения перечислены явно.
