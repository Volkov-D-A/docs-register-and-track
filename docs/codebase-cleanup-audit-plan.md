# Поэтапный план аудита избыточного кода Docflow

## Цель и границы

Выявить и последовательно устранить устаревшие реализации, недостижимый код,
неактуальную совместимость, лишние данные и вычисления, дублирующие пути,
устаревшие тесты и инфраструктуру. Аудит охватывает production-код, контракты,
схему БД, фоновые процессы, сборку, тесты и эксплуатационные документы.

Этот документ — план работ, а не заключение об уже найденных дефектах.
Названия файлов и механизмов ниже задают области проверки; сами по себе они
не являются основанием для удаления. Текущий функционал сохраняется, если
отказ от него не согласован отдельно. Перепроектирование ради сокращения строк
и обновление зависимостей без связи с находками в задачу не входят.

## Правила доказательства и учёта

Для каждого кандидата проверять цепочку в обе стороны:

`пользовательский/операционный сценарий → React → Wails → desktop service → HTTP client → route → server service → repository → SQL/storage → outbox/worker → SSE/UI/внешний эффект`.

У CLI, startup, миграций, backup/restore и фоновых задач отдельные точки входа.
Учитывать вызовы через интерфейсы, регистрацию обработчиков, строки событий,
reflection, JSON, SQL, embed, генерацию, build tags и платформенные файлы.
Отсутствие текстовых ссылок, нулевое покрытие или отсутствие событий в локальном
логе не доказывают неиспользуемость. Наличие единственного вызова из теста
не доказывает необходимость production-метода.

Вести реестр находок в этом документе либо в одном сопутствующем файле в `docs/`.
Не создавать отдельную иерархию audit/runbook. Для каждой записи фиксировать:

- ID, этап, файлы/символы и затронутый сценарий;
- категорию: недостижимый код, устаревшая совместимость, лишние данные,
  дубль, тестовый хвост, инфраструктура или документация;
- производителя и всех потребителей, включая тестовых и внешних;
- доказательства: ссылки на код, команды анализа, проверенную конфигурацию сборки;
- последствия удаления: контракт, сохранённые данные, безопасность, побочные эффекты;
- решение: удалить, упростить, заменить, сохранить или требуется уточнение;
- уверенность, риск, зависимые находки и минимальную проверку;
- статус: кандидат → доказан/сохранён/отложен → исправлен → проверен;
- для сохранённого/отложенного: конкретную причину и условие пересмотра.

Отдельно вести матрицу покрытия: область × production/контракты/данные/тесты/
сборка/документация. Для каждой ячейки — результат, находки либо ограничение.
«Просмотрен каталог» без проверки связей не считается завершением области.

## Этап 0. Зафиксировать исходное состояние

1. Зафиксировать commit, состояние worktree и пользовательские изменения.
   Последующие выводы привязывать к этой базе; не смешивать очистку с чужими правками.
2. Сверить `AGENTS.md`, `README.md`, `docs/tech_docs.md`, `go.mod`,
   `frontend/package.json`, `Makefile` и `build/make/checks.mk` с фактической структурой.
3. Составить перечень поддерживаемых платформ и режимов: Linux/Windows,
   Wails dev/release, server, CLI, integration, production Compose, recovery.
4. Зафиксировать допустимые версии клиентов, HTTP API, схемы и архивов.
   Разделить защиту от несовместимого состояния и поддержку старого формата.
   Если политика поддержки неизвестна, пометить зависимые удаления как отложенные.
5. Разделить tracked-исходники, tracked-генерацию, локальные артефакты и внешние данные.
   Например, `frontend/.test-build` и `frontend/dist` не считать мёртвым исходным кодом.
6. Описать доступность Docker, PostgreSQL, Wails и инструментов целевых ОС.
   Не запускать полный baseline автоматически: записать известные проверки,
   воспроизводить только ошибки, мешающие оценке конкретной находки.

**Результат:** исходная база, границы поддержки, матрица областей и ограничения среды.

## Этап 1. Построить карту точек входа и зависимостей

1. Разобрать `main.go`, `cmd/`, `internal/desktop/app`, frontend `main.tsx`,
   `App.tsx`, маршрутизацию, регистрацию Wails, HTTP routes и CLI-команд.
2. Найти startup/shutdown hooks, worker, таймеры, подписки, обработчики событий,
   embed-ресурсы и генераторы. Отметить входы, доступные только администратору,
   при первом запуске, ошибке, восстановлении или остановке.
3. Построить production-граф импортов Go отдельно от test-графа, с учётом
   тегов и Linux/Windows. Проверить транзитивные границы desktop/server/shared.
4. Построить граф frontend imports/exports, динамических импортов, конфигурационных
   реестров и ссылок на generated bindings. Найти недостижимые подграфы,
   включая циклы, которые ссылаются только друг на друга.
5. Сопоставить интерфейсы портов, реализации и регистрацию в composition root.
   Искать реализации и методы, оставшиеся только ради тестов или старой сборки.

**Результат:** карта достижимости с перечисленными корнями и исключениями.

## Этап 2. Выделить незавершённые переходы и совместимость

1. Сопоставить `docs/document-deadline-control-plan.md`, журнал перехода
   `docs/document-deadline-control-changes.md`, `docs/next-updates.md` и код.
   Отделить уже заменённые пути от частей ещё выполняемого перехода.
2. Проверить следы прежнего монолита: прямой доступ desktop к инфраструктуре,
   старые конструкторы, setters, адаптеры, локальные бизнес-операции и конфигурацию.
3. Проверить старую и новую модели контроля сроков, прав, исполнителей,
   ознакомления, замещения и реквизитов пользователя по всей цепочке.
4. Искать legacy/deprecated/compat/fallback/TODO/FIXME, старые имена,
   альтернативные JSON-поля, маршруты, enum-коды, default и двойное чтение/запись.
   Поиск по словам использовать только как начальный фильтр.
5. Для каждой ветви совместимости записать поддерживаемого потребителя/формат,
   условие включения и условие удаления. Проверки build identity, dirty/newer schema,
   формата backup и отказа при несовместимости оценивать отдельно.
6. Проверить историю Git адресно: когда и чем заменён путь, почему оставлен.
   Возраст кода или давность изменения не использовать как доказательство.

**Результат:** карта переходов «старый путь → актуальная замена → остатки → решение».

## Этап 3. Проверить контракты между слоями

1. Для каждого HTTP route сопоставить серверный handler, client method,
   desktop adapter, Wails method, frontend caller и операционного потребителя.
   Отсутствие desktop caller не означает, что административный API не нужен.
2. Сверить `internal/models`, `internal/dto`, JSON tags, мапперы и типы frontend:
   лишние DTO, request/response-поля, параметры, повторные преобразования,
   потерянные ошибки, старые значения по умолчанию.
3. Разделить команды и ответы: поле может никогда не отображаться, но участвовать
   в авторизации, версии сущности, пагинации, повторе запроса или регистрации события.
4. Сопоставить Wails runtime registration, генератор,
   `internal/desktop/app/testdata/wails-api.json` и `frontend/wailsjs`.
   Найти API, удерживаемый только устаревшими bindings или contract-тестом.
5. Проверить строки ошибок, событий, permissions, document-kind/page keys,
   фильтров и сортировки на старые aliases и неиспользуемые варианты.
6. Для удаления внешнего контракта подтвердить политику поддержки; при изменении
   Wails обновлять bindings штатным dev/build, без ручного редактирования.

**Результат:** таблица контрактов и кандидаты на согласованное удаление во всех слоях.

## Этап 4. Проследить движение данных и бесполезную работу

1. Для каждого значимого поля/результата записать: источник → загрузка →
   преобразования → передача → конечное чтение или побочный эффект.
2. Искать SQL SELECT/JOIN/агрегации и загрузку вложенных объектов, результаты
   которых отбрасываются в repository, service, DTO или frontend.
3. Проверить HTTP/Wails-ответы и параметры, не доходящие до потребителя;
   вычисления перед ранним return, повторные запросы, немедленно перезаписываемые значения.
4. Проследить формы: initial values → state → validation → mapper → команда → SQL.
   Найти отображаемые, но не сохраняемые поля, и сохраняемые поля без чтения.
   Потерю нужных данных классифицировать как ошибку, а не повод удалить ввод.
5. Проверить Zustand stores, caches, derived state, refs и hooks:
   записи без читателей, инвалидацию без кэша, дублирующие источники состояния.
6. Сопоставить SSE/events, polling, refresh и subscriptions. Проверить дубли,
   события без подписчиков, подписки без производителей, отмену и cleanup.
7. Проверить генерацию отчётов, статистики, экспортов и временных файлов:
   какие результаты возвращаются/сохраняются и кто их затем использует.
8. До удаления «неиспользуемого результата» проверить транзакции, блокировки,
   проверки доступа, аудит, idempotency и другие эффекты вызываемой операции.

**Результат:** карта потерь и избыточных вычислений с конкретным последним потребителем.

## Этап 5. Проверить серверную реализацию и фоновые эффекты

1. Пройти routes → ports → services → repository для всех семейств:
   документы четырёх видов, связи, контроли/серии/исполнители, пользователи/права,
   справочники, журналы, рабочий стол, статистика, отчёты и администрирование.
2. Найти старые command/query handlers, неиспользуемые методы интерфейсов,
   прокси без назначения, дубли проверок и обходные пути к старой реализации.
3. Проверить `effects`, `outbox`, `liveevents`, `background`:
   производитель → транзакционная запись → доставка → обработчик → эффект.
4. Проверить типы событий и payload-поля, retry/dead-letter/admin-механизмы,
   фоновые lease, остановку задач и поведение в maintenance mode.
5. Проверить конфигурационные опции, метрики и логи: определение → чтение →
   фактическое влияние → операционный потребитель. Учесть внешние dashboards/alerts.

**Результат:** доказанные серверные хвосты и перечень сохраняемых защитных механизмов.

## Этап 6. Проверить схему, хранимые данные и backup/restore

1. Сопоставить embedded migrations с models, SQL, constraints, indexes,
   triggers/functions, views и фактическим использованием таблиц/колонок.
2. Для каждой потенциально лишней записи проверить INSERT/UPDATE, SELECT,
   JOIN, фильтры, сортировку, отчёты, каскады, ограничения и фоновые операции.
   Отдельно проверить индексы, необходимые constraints, и редкие recovery-запросы.
3. Найти старые таблицы/колонки/enum/настройки, backfill и двойное хранение.
   Различать производные значения, исторические снимки и ненужные дубли.
4. Проверить отложенные данные: pending outbox, audit snapshots, архивы,
   вложения и объекты storage могут переживать удаление их производителя.
5. Сопоставить manifest/version архивов, restore validation, staging, SMB,
   scripts и поддержку прежних форматов. Проверить связи файлов с метаданными.
6. До удаления данных определить: есть ли реальные установки, допустима ли
   потеря истории, нужны ли перенос/экспорт и какой путь отката возможен.
   Не переписывать применённые миграции и не удалять данные по догадке.
7. Проверять необходимые SQL и upgrade/restore-сценарии на изолированной БД.
   Чистая установка не заменяет проверку перехода с поддерживаемого состояния.

**Результат:** отдельный план изменения схемы/данных; неподтверждённые удаления отложены.

## Этап 7. Проверить desktop и frontend

1. Проверить desktop services, operations, serverclient, config и logging:
   ненужные wrappers, старые локальные операции, лишние поля сессии и преобразования.
2. Проверить маршруты, меню, role gates, lazy-компоненты и feature registries.
   Различать недостижимый экран и экран, скрытый текущими правами.
3. Проверить pages/components/features/modules/hooks/store/utils/constants/theme,
   неиспользуемые exports, props, состояния, стили, изображения и шрифты.
4. Найти параллельные варианты форм, фильтров, карточек и модалей после переходов.
   Объединять только при доказанном совпадении назначения и поведения.
5. Проверить Linux/Windows пути файлов, диалоги, opener/export, cancellation,
   reconnect, offline/error и session lifecycle; редкость сценария не означает устаревание.

**Результат:** список удалений и упрощений UI/desktop с проверяемыми сценариями.

## Этап 8. Проверить тесты, моки, фикстуры и ожидания

1. Связать каждый тест с актуальным сценарием/инвариантом и production-входом.
   Найти тесты удалённых API, старых DTO/прав/SQL и обхода актуального слоя.
2. Проверить `internal/server/mocks`, локальные mocks/stubs, sqlmock expectations,
   fixture factories и frontend mocks на методы, поля и ветви без живых потребителей.
3. Проверить тесты, которые сохраняют старый метод только ради компиляции,
   подменяют весь проверяемый путь или повторяют реализацию без проверки результата.
4. Сверить contract fixtures, snapshots, route matrices, permissions и Wails API
   с актуальным контрактом. Разобрать skipped/disabled tests, never-called hooks,
   слишком широкие catch-all/Any-подмены и проверки только частоты вызова.
5. Не удалять тест лишь из-за отсутствия production-вызова: negative contract,
   отказ на старый API, безопасность и recovery могут быть актуальными гарантиями.
6. Проверить integrationdb, Compose, seeds, backup fixtures, временные каталоги,
   setup/teardown, coverage scripts и frontend `.test-build` на реальные потребности.
7. Перед удалением устаревшего ожидания записать, какой актуальный инвариант
   остаётся защищён. Для значимого изменённого поведения добавить адресную проверку.

**Результат:** карта «сценарий → проверка» и очистка тестовых зависимостей вместе с кодом.

## Этап 9. Проверить сборку, зависимости и документацию

1. Проследить Make targets, `build/make/checks.mk`, `tools`, `scripts`, Dockerfile,
   Compose, Wails config, release generation и упаковку для обеих ОС.
2. Проверить неиспользуемые targets/scripts, env/config keys, mounts, ports,
   images, secret references и примеры. Учесть ручные операционные команды.
3. Проверить Go/npm dependencies после доказанных удалений; различать direct,
   transitive, test-only, platform-only и build-only зависимости.
   Для изменения Go-зависимостей выполнить `go mod tidy` и просмотреть оба diff.
4. Сопоставить release-gate, smoke, recovery и performance tooling с актуальной
   архитектурой; исключить проверки удалённого поведения и дубли без отдельного риска.
5. Исправить активные документы, команды и примеры, ссылающиеся на удалённые пути.
   Историю релизов и архивные планы сохранять как историю, обозначая их статус.

**Результат:** согласованная инфраструктура и документация без неработающих инструкций.

## Этап 10. Выполнить очистку небольшими завершёнными изменениями

1. Сначала завершить обзор этапов 0–9 и построить зависимости находок.
   Порядок удаления определять по связям, а не по размеру файла.
2. Первая очередь: доказанно недостижимые приватные участки, локальные дубли,
   неиспользуемые тестовые helpers и ресурсы без внешнего контракта.
3. Вторая очередь: сквозные методы/поля и лишние запросы. Одним изменением убрать
   producer, adapters, consumer, интерфейсы, bindings и тестовые заглушки.
4. Третья очередь: совместимость и публичные контракты после определения поддержки.
5. Четвёртая очередь: схема, persistent payloads и storage после решения о данных.
6. Для каждого изменения записать: доказательство ненужности, ожидаемое поведение,
   затронутую цепочку, проверку, результат и способ отката.
7. После удаления повторить адресный поиск старых символов/полей/ключей во всех
   слоях. Остатки классифицировать; не оставлять пустые adapters и фиктивные defaults.
8. Удалять опустевшие файлы, пакеты, зависимости и генерацию в той же цепочке.
   Не объединять независимую функциональную переделку с очисткой.

**Результат:** небольшие проверяемые diff, каждый закрывает целую группу связанных хвостов.

## Этап 11. Проверить результат и закрыть аудит

Проверки выбирать по риску, без автоматического полного прогона после каждой правки:

| Изменение | Минимальная достаточная проверка |
| --- | --- |
| Приватный Go-код / тестовый helper | Затронутый тест или пакет; компиляция потребителей при изменении интерфейса |
| UI, state, hooks | Адресный frontend-тест; lint/build, если риск связан с импортами или типами |
| HTTP/DTO | Контрактный тест клиента и handler; интеграция при риске реального persistence |
| Wails API | Штатная регенерация через dev/build и проверка bindings contract/diff |
| SQL, миграции, транзакции | Изолированная PostgreSQL-проверка; `make integration-test`, если узкая проверка недостаточна |
| Outbox/SSE/lifecycle | Доставка и идемпотентность; race только для затронутой конкурентной логики |
| Backup/restore/storage | Затронутый интеграционный сценарий создания/восстановления и совместимости |
| Сборка / platform-код | Затронутая целевая сборка или smoke; явно отметить непроверенную ОС |
| Markdown-ссылки | `make docs-links-check` |

Перед тяжёлым запуском объяснить проверяемый риск. Учесть, что текущий
`make integration-test` включает не только PostgreSQL, но и backup-интеграцию.
Полный `make release-gate` использовать при подготовке релиза или обоснованной
межсистемной приёмке, а не как повторяющийся шаг каждого удаления.

Критерии завершения:

- Все области матрицы просмотрены, исключения перечислены явно.
- У каждой находки есть доказательство и конечное решение; отложенные не скрыты.
- Для удалённых путей нет активных producers, consumers, mocks и документации.
- Для удалённых данных определены переход, сохранение нужной истории и восстановление.
- Защита прав, аудит, idempotency, транзакции и lifecycle не потеряны при упрощениях.
- Известно, какие проверки выполнены, что они доказывают и что выполнить не удалось.
- Итог содержит перечень удалённых механизмов, сохранённой совместимости с причинами,
  остаточных рисков и последующих действий. Число удалённых строк — дополнительная
  метрика, а не критерий качества и полноты аудита.

## Предотвращение повторного накопления

После очистки оставить только полезные ограничения: архитектурные границы,
актуальные contract-тесты и адресные проверки регрессий. Новые линтеры и анализаторы
вводить, если они обнаруживают подтверждённый класс пропусков с приемлемым шумом.
Диагностику TypeScript unused, Go static/dead-code и frontend dependency/export
анализ использовать как источник кандидатов с учётом динамических входов,
генерации и платформ; инструменты и версии выбирать на этапе выполнения.

При следующей замене механизма сразу фиксировать удаляемый старый путь,
потребителей, условие завершения перехода и судьбу сохранённых данных.
