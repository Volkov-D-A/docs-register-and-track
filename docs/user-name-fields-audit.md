# Анализ изменений реквизитов пользователя

## Результат реализации

Цепочки регистрации, административного редактирования, собственного профиля и первоначальной настройки переведены на фамилию, имя, отчество и `noPatronymic`. Общая серверная нормализация очищает отключённое отчество и обрезает пробелы, проверяет обязательность и предел 100 Unicode-символов. Формы используют `UserNameFields`; первоначальный логин фиксирован — `admin`.

Существующая `001_core_users` создаёт четыре поля и вычисляемый `full_name`; существующая 007 допускает полный снимок длинного имени в аудите. Количество миграций не изменено; `down` продолжает удалять таблицу целиком. Обычные SELECT пользователей и выборки соисполнителей читают компоненты. Подписи авторов документов, вложений, журналы, статистика и аудит резервного копирования используют вычисляемый столбец или вычисляемый `dto.User.FullName`.

Обновление профиля возвращает 200 и канонический DTO; desktop/Wails передают его в Zustand. Защита от ответа после смены сессии сохранена. Bindings сгенерированы штатной Linux-сборкой Wails в локальном режиме разработки.

## Найденные технические хвосты

| Остаток | Решение и основание |
| --- | --- |
| Независимый `models.User.FullName` и `fullName` в командах записи | Удалены; модель вычисляет имя методом, запросы содержат отдельные поля. Старый входной JSON отвергается строгим decoder. |
| Запись в обычный `users.full_name` | Удалена из repository, SQL-фикстур и генератора данных `tools/dbperf`; generated column не принимает самостоятельную запись. |
| Частичные пользователи в выборках соисполнителей | SELECT/Scan обычных и регулярных поручений переведены на компоненты; mapper получает данные для новой подписи. |
| Прежний предел 255 символов в `admin_audit_log.user_name` | В существующей 007 заменён на TEXT: три компонента по 100 символов дают до 302 символов с пробелами. Добавлен интеграционный сценарий длинного ФИО и аудита входа. |
| Старая сигнатура первоначальной настройки и фиксированное ФИО «Администратор» | Контракты формы, Wails, HTTP, repository и тестовых клиентов обновлены. Логин `admin` сохранён как требование. |
| `CreateInitialAdmin` в generated mock `UserStore` | Удалён: этого метода нет в `ports.UserStore`, вызовов и тестовых ожиданий нет. Первоначальная настройка имеет свой интерфейс. |
| Копирование исходной формы в Zustand после сохранения профиля | Заменено каноническим DTO сервера; самостоятельное формирование новой подписи на клиенте не требуется. |
| Заполнение старого `fullName` при отмене редактирования профиля | Заменено сбросом формы; повторное открытие загружает сохранённые компоненты. |
| Повторное заполнение реквизитов пользователя после асинхронной загрузки прав | Удалено из `UsersTab`: второй ответ обновляет права и замещение, не перезаписывая уже редактируемые поля имени. |
| Передача всей записи, включая read-only `fullName`, в редактируемую форму | Заменена явным заполнением реквизитов; непосредственно изменяемые значения формы и список пользователей типизированы. |
| Старые SQL-строки, моки, ожидание 204 и однословные именованные фикстуры | Переведены на новые поля/ответ; полезные сценарии сохранены. Для отсутствия отчества используется явный признак. |
| Упрощённая таблица `users` в интеграционном backup-аудите | Заменена настоящей схемой через `integrationdb.Open`; проверяются и расписание без пользователя, и вычисляемое имя пользовательского инициатора. |
| Неиспользуемое форматирование `UpdateProfileRequest.FullName` | Удалено; профиль возвращает пользовательский DTO, метод запроса ему не нужен. |

## Обоснованные сохранённые поля

| Поле или путь | Подтверждённое назначение |
| --- | --- |
| `dto.User.fullName` | Подписи шапки, исполнителей, соисполнителей, замещающих и списков пользователей; только ответ сервера. |
| Generated `users.full_name` | JOIN авторов/участников, сортировка, группировки статистики, журнал документа и SQL-аудит резервирования; вычисляется БД. |
| `ApplicantFullName` / `applicant_full_name` | ФИО заявителя обращения, не учётная запись пользователя. |
| ФИО внешних ознакомляемых приказов | Самостоятельные записи внешнего ознакомления, включая сохранение уже подтверждённых лиц. |
| `user_name`, имена в details и payload событий | Исторические снимки аудита; не являются редактируемыми реквизитами пользователя. Новые события используют вычисляемое имя. |
| `dto.User.FullName` в серверном сервисе вложений | Сервис получает DTO через principal; это действующий ответ, а не удалённое поле `models.User`. |

## Приёмка и эксплуатация

Проверки охватывают нормализацию и Unicode, HTTP-регистрацию и редактирование, канонический профиль и защиту сессии, desktop-контракты, выборки пользователей/соисполнителей, ограничения и вычисляемый столбец PostgreSQL, атомарный audit/outbox, связанные документы, статистику и события. Компонентные сценарии проверяют флаг, очистку значения/ошибки, повторную обязательность, первоначальную настройку, регистрацию, профиль и отмену.

Выполненные проверки:

- Точечные Go-тесты общей логики, DTO, серверных handlers/services/repository, desktop services/serverclient, Wails-контракта приложения, соответствия mocks/ports и embedded migrations — пройдены.
- Интеграционные PostgreSQL/S3-тесты `internal/server`, `repository`, `effects`, `background`, `backup` — завершены. Единственный сбой старого ожидания 204 исправлен; этот сценарий повторно прошёл. Новые сценарии структуры имени, максимальной длины и пользовательского backup-аудита также прошли.
- Vitest: `userNameFields.test.tsx` и `sessionLifecycle.test.tsx` — 17 тестов пройдены.
- `DOCFLOW_LOCAL_BUILD=1 make build-linux` — штатная генерация bindings, frontend build и Linux/Wails-сборка пройдены. После последующих изменений форм выполнены `tsc --noEmit` и ESLint затронутых файлов — пройдены.
- `make docs-links-check` — пройден. Diff прикладных файлов проверен; штатный Wails generator оставляет табуляцию в двух пустых строках нового класса `InitialSetupRequest`, generated файл вручную не исправлялся.

Полный release gate не запускался. Smoke-тесты собранного сервера и восстановления, требующие отдельного окружения/архива, в обычном integration-прогоне пропущены по отсутствию соответствующих переменных окружения.

Существующие данные не переносились и не удалялись. Для уже применённой прежней 001 требуется отдельно пересоздать конкретное тестовое окружение; старые архивы несовместимы при том же номере версии схемы. Проверка полноценного backup/restore нового архива и визуальная приёмка в запущенном desktop остаются ручными сценариями: создание администратора, оба варианта отчества, редактирование/отмена/повторный вход, подписи в шапке, исполнителях, журнале и статистике. Сборка Windows отдельно не выполнялась.
