# План разделения AttachmentService

Дата: 7 сентября 2026 года. Статус: запланировано, реализация не начата.
Основание: риск №3 из [код-ревью перехода на сервер](server-transition-code-review.md).

Цель — заменить смешанный сервис двумя самостоятельными реализациями и оставить
в Wails только операции, используемые интерфейсом. Desktop не содержит серверный
сервис ни как встроенный тип, ни как поле с делегированием вызовов.

## Подтверждённое исходное состояние

- `internal/services/attachment.go` содержит desktop- и server-конструкторы,
  возвращающие один тип `AttachmentService`; выбор реализации происходит через
  ветки `s.server != nil` и `s.server == nil`.
- `internal/app/app.go` публикует этот тип в рабочем приложении и в генераторе
  bindings. Из 20 экспортированных методов UI использует 10.
- `MaxUploadSize` обращается к незаданному в desktop `settingsService` и вызывает
  panic. Wails v2.15.0 перехватывает panic в диспетчере при текущих настройках;
  завершение всего процесса этим сценарием не подтверждено.
- Сервер уже имеет узкий интерфейс `attachmentAPI`, а desktop — HTTP-контракт
  `serverclient.AttachmentClient`. Они служат границами разделения.
- Существующие тесты связывают серверные проверки прав с выбором локальных файлов.
  Их необходимо разделить с сохранением проверяемых сценариев.

## Целевая структура

| Область | Desktop | Сервер |
| --- | --- | --- |
| Тип | `services.AttachmentService` | `services.ServerAttachmentService` |
| Основной файл | `internal/services/attachment_desktop.go` | `internal/services/attachment_server.go` |
| Время жизни | Один экземпляр на desktop-приложение | Экземпляр на HTTP-запрос с текущим principal |
| Данные | Только `serverclient.AttachmentClient` | Repository, настройки, principal, document access, object storage, assignments, substitutions, storage mutation coordinator |
| Файлы | Нативный диалог, чтение выбранных файлов, сохранение в Downloads, открытие файла/папки | Streaming запроса/ответа и работа с object storage |
| Права и эффекты | Получение результата HTTP API | Проверки доступа, лимиты и типы файлов, metadata, journal/outbox, удаление и reconciliation |
| Wails | Публикуется только этот тип | Никогда не регистрируется в `Bind` |

Оба типа остаются в существующем Go-пакете `services`. Это разделение реализаций
и зависимостей объектов; выделение всего desktop-кода в отдельный пакет и удаление
транзитивных Wails-зависимостей из серверной сборки требуют отдельной работы.

Сохранение имени desktop-типа оставляет действующим путь
`frontend/wailsjs/go/services/AttachmentService`. Имена HTTP endpoints, форматы
DTO и действующие правила доступа сохраняются.

## Контракт desktop

Точный список публичных методов:

- `Upload`, `UploadForAssignment`;
- `GetList`, `GetAssignmentFiles`;
- `Delete`, `BulkDeleteOlderThan`, `ReconcileStorage`;
- `DownloadToDisk`, `OpenFile`, `OpenFolder`.

`BulkDeleteOlderThan` и `ReconcileStorage` используются настройками хранилища;
они остаются в UI-контракте и вызывают защищённые административные HTTP endpoints.

Клиент, lifecycle, metrics и адаптеры ОС передаются при создании объекта.
Конструктор `NewDesktopAttachmentService` возвращает сервис, callback
инициализации Wails-контекста и ошибку конфигурации. Callback вызывается из
`OnStartup`, хранит контекст в закрытом состоянии и не является публичным методом
сервиса. До инициализации выбор файлов возвращает контролируемую ошибку.
Обязательный HTTP-клиент проверяется при создании; отсутствие клиента не включает
локальный доступ к данным. Metrics могут оставаться необязательными.

Для тестов предусматриваются подменяемые функции выбора файлов, определения
Downloads и запуска системного приложения. Они передаются конструктору и не
публикуются как сеттеры. Доступ к startup-состоянию должен быть безопасен при
конкурентном вызове операций.

## Контракт сервера

Сохранить методы существующего `internal/server/attachments.go:attachmentAPI`:
`MaxUploadSize`, `UploadContent`, `UploadAssignmentContent`, `GetList`,
`GetAssignmentFiles`, `AuthorizeDownload`, `StreamAttachment`, `Delete`,
`BulkDeleteOlderThan`, `ReconcileStorage`.

`NewServerAttachmentService` возвращает новый серверный тип. Зависимости
передаются конструктору, включая assignments, substitutions и metrics, которые
сейчас устанавливаются сеттерами. Сохранить существующую семантику необязательных
зависимостей и storage mutation coordinator; обязательные зависимости проверять
при построении объекта. Серверный объект не содержит HTTP-клиент, Wails-контекст,
диалог выбора файлов, Downloads или запуск приложений ОС.

Чистые вспомогательные функции размещаются по владельцу: reconciliation — на
сервере; безопасные имена, уникальные файлы и проверка локального пути — в desktop.
Общий код выделяется только при реальном использовании обеими реализациями.

## Последовательность реализации

1. Зафиксировать рабочие контракты и перечень сценариев существующих тестов.
   Добавить проверку точного списка методов desktop и запрета серверного типа в
   обеих регистрациях Wails. Проверка должна выявлять нынешнюю избыточную публикацию.
2. Выделить `ServerAttachmentService` и перенести серверные ветки без изменения
   правил доступа и порядка побочных эффектов. Переключить фабрику в
   `internal/server/management.go` на новый тип. Сохранить соответствие `attachmentAPI`.
3. Превратить `AttachmentService` в самостоятельную desktop-реализацию с десятью
   методами. Перенести файловые функции; удалить обращения к repository/storage и
   переключение режимов по наличию клиента. Удалить серверный путь `DownloadToDisk`:
   сервер отдаёт поток, а сохранение на диск выполняет только desktop.
4. Обновить создание desktop в `internal/app/app.go`, передачу lifecycle/metrics и
   callback `OnStartup`. Синхронно обновить `NewBindingsWailsOptions` и проверки
   composition root. Нулевой экземпляр для генератора используется только для
   отражения типов, без выполнения операций и подключения инфраструктуры.
5. Разделить тесты на `attachment_desktop_test.go` и `attachment_server_test.go`.
   Серверные тесты загрузки через локальный путь заменить вызовами streaming-методов;
   выбор файлов проверять отдельно через fake HTTP-клиент. Обновить относящиеся к
   вложениям проверки в `lifecycle_setters_test.go` под конфигурацию конструктором.
6. Удалить смешанный `attachment.go`, legacy-конструктор `NewAttachmentService` и
   прежний `NewAttachmentServiceWithClient` после перевода всех вызовов. Удалить
   закомментированные base64-тесты; актуальные сценарии перенести в исполняемые тесты.
7. Выполнить `make wails-bindings` и проверить полученный diff. В bindings вложений
   должны остаться только десять разрешённых методов; связанные модели генератор
   удаляет лишь тогда, когда они больше не нужны другим сервисам. Завершить проверки
   и обновить статус риска №3 в ревью.

Шаги являются частями одного завершённого изменения: промежуточная совместимость
не должна оставлять смешанный сервис или небезопасные bindings в конечном результате.

## Проверки поведения

- Desktop: загрузка к документу и поручению передаёт правильные идентификаторы,
  имя, размер и поток; отмена диалога не вызывает HTTP; ошибка чтения файла
  корректно завершается; локальный файл закрывается.
- Desktop: скачивание закрывает HTTP body, сохраняет безопасное уникальное имя,
  не перезаписывает существующий файл и удаляет частичный файл при ошибке.
  Проверки Downloads и символических ссылок сохраняются; тесты не запускают GUI.
- Desktop: списки, удаление и административные операции передаются HTTP-клиенту;
  ошибки сервера доходят до вызывающего кода; timeout, cancellation, shutdown и
  текущие метрики сохраняются при переносе.
- Сервер: права на документы/поручения, замещения, лимиты и типы файлов;
  повторная проверка возможности прикрепления после upload; компенсация ошибок
  object storage; metadata и journal/outbox; чтение, удаление, массовое удаление,
  reconciliation. Сохранить существующий порядок операций.
- Wails: точный список методов самого Go-типа и сгенерированных JS/TS; отсутствие
  `Startup`, сеттеров зависимостей, `AuthorizeDownload`, `MaxUploadSize`, streaming
  методов и параметров `context.Context`/`io.Reader`/`io.Writer` у desktop bindings.
  Список типов в рабочей регистрации совпадает с регистрацией генератора.
- HTTP: существующие streaming-тесты, admin permissions, безопасные заголовки и
  блокировка вложений в maintenance продолжают проходить.

Команды проверки при реализации:

```sh
env GOCACHE=/tmp/docflow-go-build-cache go test ./internal/services ./internal/server ./internal/serverclient ./internal/app
env GOCACHE=/tmp/docflow-go-build-cache go test -race ./internal/services ./internal/server ./internal/serverclient ./internal/app
env GOCACHE=/tmp/docflow-go-build-cache go vet ./internal/services ./internal/server ./internal/serverclient ./internal/app
make wails-bindings
npm --prefix frontend run lint
npm --prefix frontend run build
```

Дополнительно выполнить существующий PostgreSQL integration test
`TestAttachmentAPIStreamsAndPersistsLifecycleIntegration` на тестовой БД через
штатное integration-окружение репозитория. Запустить относящиеся к вложениям
frontend-тесты, включая завершение поручения и историю серии. Если нативное
окружение доступно, проверить вручную выбор файлов, скачивание и открытие в ОС.
Отдельно указать проверки, недоступные в окружении реализации.

## Критерии завершения и границы

- Существуют два независимых типа; в desktop отсутствуют server fallback и
  зависимости доступа к данным, в серверной реализации отсутствуют desktop-операции.
- Wails публикует ровно десять методов вложений; генерация воспроизводима.
- UI-сценарии, HTTP-контракты, проверки прав, streaming и transactional effects
  сохранены; перечисленные проверки выполнены с явно указанными ограничениями.
- Риск №3 для вложений закрыт в ревью. Избыточные методы других Wails-сервисов
  остаются отдельной задачей и не считаются исправленными этим разделением.
- Остальные риски ревью, общая переделка auth и миграции схемы не входят в это
  изменение. Принятое решение по риску №2 сохраняется.
