# План разделения ФИО пользователя

Статус: реализовано в коде; результаты проверок и анализа технических хвостов зафиксированы в `docs/user-name-fields-audit.md`. Существующий локальный стек и его данные не пересоздавались.

## 1. Требования и принятые решения

- Вместо единственного редактируемого ФИО пользователь имеет `lastName` (фамилия), `firstName` (имя), `patronymic` (отчество), `noPatronymic` (признак «Нет отчества»).
- Фамилия и имя обязательны. Отчество обязательно, когда `noPatronymic=false`. Когда признак включён, поле недоступно для ввода, очищается и не участвует в отображении, хранении введённого текста и проверке обязательности. При выключении признака отчество нужно заполнить заново.
- Сервер обрезает пробелы по краям всех частей имени. Пробельные строки не считаются заполненными. Не ограничивать имена только кириллицей и не запрещать дефисы, апострофы или составные имена. Определить одинаковые ограничения длины в серверной валидации, БД и формах.
- Единственное правило отображения: «Фамилия Имя Отчество» либо «Фамилия Имя». Между частями один разделительный пробел; внутренние пробелы составных имён сохраняются. `fullName` в ответах остаётся вычисляемым представлением для таблиц, подписей и списков выбора, а в запросах записи удаляется.
- Подтверждено пользователем: существующие пользователи тестовые, перенос их старого ФИО не нужен. Автоматическое разбиение произвольной строки и постоянный слой совместимости со старым вводом не требуются.
- По уточнению пользователя новую миграцию не добавлять: изменить существующую `001_core_users`. Для первоначального администратора запросить отдельные поля ФИО и признак отсутствия отчества; при создании логин фиксирован — `admin`.
- Не менять реквизиты заявителей обращений (`applicantFullName`) и внешних ознакомляемых приказов (`AcknowledgmentFullNames`, `AdministrativeOrderAcknowledgmentPerson.FullName`): это самостоятельные сущности.
- Реализация включает отдельный итоговый анализ технических хвостов с удалением подтверждённых остатков в затронутой цепочке.

## 3. Модель, валидация и схема БД

1. Добавить четыре поля в `models.User`, запросы создания пользователя, административного изменения и изменения собственного профиля. Убрать независимо присваиваемое поле `models.User.FullName`; заменить его методом вычисления отображаемого имени. Разместить нормализацию, валидацию и форматирование в независимом общем пакете без зависимостей от server, desktop и Wails; использовать одни правила для всех серверных входов.
2. Добавить четыре поля в `dto.User`, сохранить `dto.User.FullName` как вычисляемый ответ. Обновить mapper и все места создания неполных `models.User`, особенно соисполнителей: после удаления присваиваемого `FullName` им нужны компоненты имени, чтобы mapper не вернул пустое имя.
3. В `users` хранить `last_name`, `first_name`, `patronymic`, `no_patronymic`. Выбрать единое пустое значение отчества — пустую строку, без параллельного использования NULL. Добавить ограничения непустых фамилии/имени и согласованности отчества с признаком, а также согласованные пределы длины.
4. Рекомендуемый способ сохранить SQL-проекции имён: заменить обычный `users.full_name` на generated stored column, вычисляемый из четырёх полей. Он нужен многим существующим JOIN, сортировкам и группировкам, является только представлением и не принимает независимые записи. Использовать допустимое для generated column immutable выражение; проверить его на используемой версии PostgreSQL. Согласовать результат с форматированием в Go тестами, включая составные имена и отсутствие отчества.
5. Изменить определение `users` непосредственно в `001_core_users.up.sql`: новые реквизиты, ограничения и вычисляемый `full_name` создаются сразу. Новую миграцию не добавлять, число и версии embedded migrations не менять. Проверить соответствие `001_core_users.down.sql`: он уже удаляет таблицу пользователей, отдельное восстановление старого цельного ФИО не требуется. Не вводить обходной ALTER или переходный слой миграции в runtime-код.
6. Для проверки использовать заново созданную изолированную тестовую БД с обновлёнными миграциями и фикстурами. Уже применённая `001_core_users` автоматически повторно не выполнится; прежняя схема с тем же номером версии не станет новой после обычного запуска миграций. Поэтому существующее тестовое окружение требует явного пересоздания схемы и тестового набора, а не переноса старых ФИО. До выполнения такого шага определить конкретное окружение и объём пересоздаваемых данных; не выполнять скрытое удаление пользователей, документов или томов. В этой задаче планирования данные не изменяются.

**Результат:** один источник реквизитов, один контракт отображения, нет независимо изменяемых копий ФИО и нет неявного угадывания старых данных.

## 6. Минимальные проверки по рискам

- Общая логика: фамилия/имя обязательны; пустое и пробельное отчество; оба значения признака; присланное отчество при включённом признаке; нормализация краевых пробелов; составные имена, Unicode, дефисы, пределы длины.
- HTTP и desktop-контракт: создание, административное изменение, собственный профиль, вход/текущий пользователь и первоначальная настройка; канонический ответ; сохранение правил доступа; отсутствие записи через старый `fullName`; первоначальный администратор получает введённые реквизиты и логин `admin`.
- Изолированный PostgreSQL: обновлённая `001_core_users` и полный набор существующих миграций на пустой БД; относящийся к изменению `up`/`down`; generated column и CHECK; совпадение SQL/Go отображения; создание администратора; изменение пользователя/профиля вместе с audit/outbox. Дополнительно проверить проекции соисполнителей, документов, вложений, статистики и backup audit там, где изменены SQL или структура Scan. Использовать `make integration-test` либо узкий запуск на заново созданном отдельном integration-стеке.
- Формы и store: создание, заполнение редактирования, включение/выключение признака, очистка ошибок и старого отчества, отмена, переключение пользователя, канонический ответ сервера, ответ после завершения сессии. Проверять существующей инфраструктурой frontend; при отсутствии компонентного harness выбрать узкий тест логики и записать ручные сценарии, не создавать инфраструктуру без необходимости.
- Generated bindings и TypeScript: штатная генерация, проверка diff и frontend build для риска рассогласования DTO/Wails. Более широкие Go/frontend проверки запускать только по оставшемуся конкретному риску.
- Ручная приёмка в desktop: первоначальный администратор, создание пользователя с отчеством и без, редактирование администратором и самим пользователем, шапка, повторный вход, исполнитель/соисполнитель/замещающий, автор документа/вложения, журнал и статистика.
- Backup/restore: проверить восстановление архива, созданного на обновлённой схеме. Архивы прежней схемы не считать совместимыми: при неизменном номере версии штатная проверка версии миграций не различит старую и новую структуру `users`. В инструкции тестового окружения зафиксировать пересоздание БД и использование новых архивов; не добавлять скрытую конвертацию при восстановлении.

## 8. Критерии завершения

- Во всех путях создания и изменения пользователя сохраняются четыре новых реквизита; отключённое отчество не используется и не возвращается как заполненное.
- Новая схема создаётся изменённой `001_core_users` без дополнительной миграции; первоначальный администратор создаётся с введёнными реквизитами и логином `admin`.
- После перечитывания профиля и повторного входа отдельные поля и отображаемое имя совпадают с сохранёнными данными.
- Все затронутые подписи, выборки, журналы и статистика работают; ссылки между сущностями и доступ продолжают определяться по ID и правам.
- Нет независимой записи цельного ФИО пользователя и устаревших методов, моков или фикстур, обслуживающих такой ввод.
- Выполнен и описан анализ технических хвостов; причины сохранения оправданных употреблений `fullName` зафиксированы.
- Итоговый отчёт содержит выполненные проверки, ручные сценарии, ограничения и явно невыполненные проверки.
