# План серверного резервирования и полного отказа от MinIO

Дата: 10 сентября 2026 года.

Статус: основной серверный цикл реализован: AWS SDK, прямой SMB, настройки и
расписание в панели, согласованный снимок v3, восстановление v2/v3 и автономная
панель. Интеграционные проверки выполнены на изолированном Samba; проверка
целевого FreeNAS и эксплуатационная приёмка ещё требуются. Расширенный smoke-тест
успешно проверил CLI restore v2, серверный backup/restore v3 и аварийную панель
с каталогом SMB при отсутствующей основной БД.

Инструкция установки: [Серверное резервирование](server-backup-operations.md).

Ниже сохранены исходные критерии плана. Отмечены полностью выполненные пункты;
неотмеченные включают оставшиеся проверки либо расширения:

- Проверка конкретного FreeNAS, обрывов сети, заполнения диска и измерение
  RPO/RTO на рабочем объёме требуют отдельной приёмки.
- История заданий доступна из постоянного локального журнала, результаты пишутся
  в БД; каталог SMB независимо читается аварийной панелью. Автоматического
  согласования всех трёх источников истории пока нет.
- UI показывает состояние, размер архива, ошибки, следующую дату и повтор;
  процент передачи и отдельное задание проверки произвольного архива не добавлены.
- Старые скрипты сохранены для проверки совместимости v2 и прежней автоматизации;
  они уже используют серверный S3-клиент. Новому резервированию они не нужны.
- Проверки desktop Linux/Windows и release-gate остаются частью выпуска.

## Принятые решения

- PostgreSQL хранит данные приложения, SeaweedFS — вложения через S3 API.
- Все рабочие зависимости MinIO удаляются: SDK, CLI, контейнеры, тестовые helpers.
  S3-клиент переводится на AWS SDK for Go v2.
- Достаточно Docker Compose V2. Swarm, Docker socket, привилегированный контейнер
  и монтирование SMB на хосте не требуются.
- Сервер подключается к SMB напрямую через Go-библиотеку. Адрес, общая папка,
  подкаталог, пользователь, домен, пароль, расписание и retention управляются
  через административную панель приложения.
- Desktop обращается только к версионированному API сервера.
- Общий Go-модуль выполняет backup, проверку и restore. Внешние shell-скрипты
  резервирования после перехода не нужны. `pg_dump` и `pg_restore` остаются
  штатными исполняемыми утилитами PostgreSQL, запускаемыми сервером без shell.
- Первый вариант создаёт полные копии с временным запретом обычных операций.
  После фиксации локального комплекта обслуживание заканчивается; передача на
  SMB выполняется при работающем приложении.
- Автономный режим восстановления того же бинарного файла работает без основной
  БД и имеет собственную панель, CLI и отдельную аварийную авторизацию.

## Исходное состояние

- Основной и интеграционный Compose используют `minio/mc` для S3 probe.
- `internal/storage/s3.go` и интеграционные тесты используют `minio-go/v7`.
- `backup_smb_tar.sh`, `restore_smb_tar.sh` и `scripts/smb_backup_lib.sh`
  управляют Docker, CIFS, PostgreSQL и копированием S3.
- Формат v2 содержит `database.dump`, `objects/` и внешний manifest с checksum.
- Скрипт backup останавливает сервер до окончания публикации архива на SMB.
- `internal/server/maintenance.go` и `internal/background/lifecycle.go`
  координируют запросы и фоновые процессы при работе со схемой. Это основа,
  но ещё не полноценный барьер резервирования.
- Серверный образ distroless не содержит утилит PostgreSQL: потребуется изменить
  runtime-образ, сохранив запуск от непривилегированного пользователя.

## Этап 1. Контракты, прототип SMB и формат копии

- [ ] Определить интерфейсы источника объектов, резервного хранилища, запуска
  PostgreSQL tools и координатора обслуживания; вынести общий код в
  `internal/backup`, SMB-адаптер — в отдельный пакет.
- [ ] Проверить поддерживаемость, лицензию и зависимости кандидатов Go SMB;
  выбрать библиотеку по результату прототипа с целевым NAS. Не принимать
  библиотеку, которая возвращает MinIO через транзитивные зависимости.
- [ ] Проверить SMB 2/3, используемую NAS авторизацию, signing/encryption,
  таймауты, отмену, большие файлы, Unicode, rename, flush и разрыв соединения.
  Зафиксировать поддерживаемые режимы; SMB1 не использовать.
- [x] Определить формат v3: версия приложения и схемы, время снимка, идентификатор
  комплекта, dump, перечень ключей объектов, размеры, Content-Type и SHA-256.
  Ключи S3 хранить в manifest, а файлам архива назначать безопасные внутренние
  имена: ключ объекта не должен становиться произвольным путём при распаковке.
- [x] Сохранить чтение существующего v2 через отдельный адаптер; новые копии
  писать в v3. Контрольная сумма обнаруживает повреждение, но сама по себе
  не подтверждает доверенное происхождение архива.
- [ ] Зафиксировать требования к свободному месту, предельному времени паузы,
  объёму данных и времени восстановления; измерить их на репрезентативном наборе.

Результат: выбран и проверен SMB-клиент, описан формат и ограничения первой
версии. Если целевой NAS несовместим, пересмотреть транспорт до основной реализации.

## Этап 4. Координатор согласованного снимка

- [x] Объединить взаимное исключение backup, restore и миграций с существующим
  server-worker lease. Вторая серверная инстанция не должна обходить барьер.
- [ ] Ввести обслуживание с причиной, временем начала и состоянием операции.
  Для первой версии блокировать обычные запросы целиком; отдельные admin status
  и liveness сохранять доступными. Авторизацию status сделать без записи в БД
  во время снимка; события backup писать в локальный журнал до снятия барьера.
- [x] Дождаться уже принятых запросов, включая streaming upload/download, затем
  остановить и дождаться всех фоновых записей: outbox, cleanup, startup work,
  reconciliation и обновлений статистики. Самой отмены context недостаточно.
- [x] При таймауте drain не начинать dump; восстановить только безопасное состояние.
  Не допустить, чтобы ReconcileSchema сам снял обслуживание в середине backup.
- [x] Сделать dump и экспорт всех объектов при удерживаемом барьере. Проверить
  наличие файлов для активных вложений; отдельно учитывать pending delete и
  соответствующие outbox-события, не требуя уже удалённый объект безусловно.
- [x] Зафиксировать локальный manifest и файлы на постоянном диске. Только после
  этого снять барьер. Если локальный комплект неполон, не считать его резервной
  копией; при ошибке backup безопасно возобновить приложение.
- [x] Определить восстановление состояния после аварийного завершения процесса.
  Частичный снимок удаляется/помечается невалидным; готовый может быть отправлен
  повторно. Прямые сторонние записи в БД/S3 во время снимка не поддерживаются.

Приёмка: конкурентные изменения документов, upload/delete и outbox не нарушают
связность снимка; timeout и рестарт не публикуют неполный комплект.

## Этап 5. SMB, задания и расписание

- [x] Реализовать проверку подключения: запись, чтение, rename, flush и удаление
  только временного файла проверки в выбранном подкаталоге.
- [ ] Записывать архив под уникальным временным именем; после закрытия/flush
  проверять чтением размер и SHA-256. Публиковать manifest-маркер последним.
  Не предполагать атомарность нескольких файлов; гарантии проверить на NAS.
- [x] Ввести состояния queued, snapshotting, staged, transferring, verifying,
  completed, failed, cancelled и interrupted. Завершение локального снимка
  не означает наличие удалённой копии.
- [x] После разрыва повторять передачу готового локального комплекта с backoff;
  сохранять его при рестарте. Первая версия может начинать передачу заново.
  Ограничить очередь, число попыток и staging; при заполнении не создавать
  бесконечно новые локальные снимки и не удалять молча неотправленные данные.
- [x] Добавить ежедневное/еженедельное расписание с IANA timezone. Зафиксировать
  поведение при DST и простое: один пропущенный запуск после восстановления,
  без серии догоняющих запусков. Исключить дубли при рестарте и ручном запуске.
- [x] Retention выполнять только после успешной публикации; учитывать возраст,
  минимальное количество копий и комплекты, используемые restore. Никогда не
  удалять последнюю исправную копию. Удалять только распознанные комплекты
  нашего формата, не чужие файлы NAS.
- [ ] Хранить историю в БД и локальном журнале; после восстановления БД сверять
  каталог SMB с manifest, поскольку история самой копии может отсутствовать
  в её dump. Не сохранять пароли в manifest и диагностике.

Приёмка: проверены обрыв, недоступный NAS, запрет записи, заполнение диска,
рестарт во время передачи и retention. Неуспешный backup не удаляет старые копии.

## Границы первой версии и порядок поставки

Этапы выполняются последовательно; каждый заканчивается проверяемым результатом.
Удаление старых скриптов допускается только после приёмки нового восстановления.
До этого переходные команды сохраняют текущую эксплуатационную процедуру.

В первую версию не входят PITR/WAL, инкрементальные копии, backup без паузы,
автоматическая замена рабочего окружения, Kerberos без отдельной проверки NAS,
автоматическое управление Docker из приложения и шифрование содержимого архивов.
Если требуется шифрование архивов, для него нужен отдельный контракт ключей и
восстановления; ключ настроек не считается автоматически ключом резервных копий.

Критерий завершения: администратор через панель настраивает SMB и расписание,
создаёт проверенную удалённую копию и восстанавливает её в пустое окружение при
недоступной исходной БД. Compose работает без Swarm, MinIO и привилегий монтирования.
