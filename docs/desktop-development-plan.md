# План разработки рабочего стола

Основа: `docs/desktop.md`. Цель — заменить текущую страницу активности рабочим столом с единым переключателем «Исполнение / Контроль» для поручений и ознакомлений, правами из серверной матрицы и согласованными счётчиками и списками. Порядок ниже рассчитан на последовательные, проверяемые изменения; завершение каждого этапа сохраняет работоспособность клиента и сервера.

## 1. Зафиксировать правила отображения и измерения

1. Составить таблицу состояний для обоих режимов поручений и ознакомлений: критерий доступности режима, статусы строк, счётчики, сортировка, действие по клику, пустое состояние. Для поручений явно разделить `new`, `in_progress`, `returned`, просрочку, близкий срок и `completed` (ожидает приёмки); определить границу «близкого срока» и дату/часовой пояс. Не смешивать число непрочитанных событий с числом задач.
2. Принять для режима контроля существующую семантику `assign`/`acknowledge` по доступным документам, а не авторство создания. Если нужен контроль только собственных назначений, сначала изменить концепцию и серверные правила. Уточнить действия соисполнителя: текущие списки включают его, но переходы статуса требуют проверки отдельно. Выделить личные поручения и задачи замещаемых без двойного счёта.
3. Зафиксировать поведение смешанного пользователя: единый переключатель текстовыми ссылками справа от имени пользователя в заголовке рабочего стола; если доступен один режим, переключателя нет. Блоки без доступа к выбранному режиму скрывать. По умолчанию выбрать «Исполнение», если оно доступно, иначе «Контроль»; выбор сохранять только в пределах текущей сессии и сбрасывать при смене пользователя/прав. Определить поведение пользователя с документными правами, но без рабочих задач, и администратора без участия в документообороте.
4. Описать переходы по карточкам и показатели, которым нужен отдельный экран списка. Для ознакомлений решить, нужен ли общий список с фильтрами или достаточно открытия документа: существующая `AcknowledgmentList` показывает задачи лишь в карточке документа.

**Результат:** спецификация сценариев и ожидаемых чисел для пользователя-исполнителя, контролёра, смешанного пользователя, замещающего, участника с частичными правами и администратора. Это основа серверных и UI-тестов.

## 2. Спроектировать серверный контракт рабочего стола

1. Сделать сервер единственным источником состава разрешённых режимов, счётчиков и строк предпросмотра. `CurrentAccessSummary` уже содержит права по видам и доступность разделов, но не персональные задачи. Определить DTO для выбранных режимов, счётчиков, ограниченного списка строк и параметров перехода; не передавать клиенту внутренние scope-поля. Состояние недоступного режима должно отличаться от доступного пустого списка.
2. Выбрать совместимый маршрут в версионированном HTTP API, например `GET /api/v1/workspace/summary` с валидируемыми параметрами режимов. Сервер проверяет режимы повторно на каждом запросе; недоступный режим не раскрывает количество или содержание задач. В desktop оставить только HTTP-адаптер и Wails-метод, без доступа к БД или `internal/server`.
3. Для крупных списков определить серверные фильтры и пагинацию. Предпросмотр рабочего стола ограничить небольшим числом строк, но счётчики считать по полному разрешённому набору. Не собирать всю таблицу в React или Go ради нескольких карточек. Если счётчик ведёт в раздел поручений, фильтр, scope, статус и временная граница в разделе должны давать тот же набор строк.
4. Проверить зависимость от `GET /api/v1/dashboard/activity`: поискать внешних потребителей и зафиксировать решение о совместимости. После переключения клиента удалить старый путь целиком, если он не является поддерживаемым внешним контрактом; иначе оставить документированный совместимый адаптер без дублирования SQL и бизнес-правил.

**Результат:** описание HTTP/Wails-контракта, таблица соответствия карточек и фильтров и решение о судьбе старого API до начала реализации.

## 3. Реализовать серверные выборки и доступ

1. В сервисе рабочего стола использовать текущего аутентифицированного пользователя и существующие проверки документных действий, participant scope и активного замещения. Для «Исполнения» выбирать собственные и замещаемые поручения, включая соисполнение; для «Контроля» — доступные по `assign` документы. Не выводить право контроля из `read`, `create`, UX-профиля или создателя поручения. Учесть частичные права по видам и доступ к конкретному документу.
2. Аналогично разделить ожидающие подтверждения ознакомления и контроль активных ознакомлений по `acknowledge` с проверкой читаемости документа. Проверить, что суммарные запросы применяют тот же scope, что операции и списки. Переиспользовать общие предикаты доступа там, где это возможно, вместо двух расходящихся SQL-реализаций.
3. Добавить агрегирующие SQL-запросы и ограниченный предпросмотр. Определить единые правила текущей итерации регулярного поручения, статусов, дедлайна и часового пояса. Ограничить объём ответа; оценить индексы и план запросов на рабочем объёме данных. Миграции добавлять только при реальной необходимости для индекса или хранения новых данных.
4. Провести цепочку DTO → HTTP handler → desktop `serverclient` → desktop service → Wails. Ошибки доступа и обслуживания сервера передавать через существующий контракт ошибок. Изменённые Wails bindings генерировать обычным `make dev-client` или сборкой, проверить их diff; вручную не редактировать.

**Проверки этапа:** точечные unit-тесты правил режимов и доступа; HTTP-тесты авторизации/валидации; SQL-интеграционные тесты на изолированном PostgreSQL для счётчиков, фильтров и пагинации. Матрица тестов: основной исполнитель, соисполнитель, замещение, контроль по одному виду, смешанные права, запрет на чужой документ, снятие права между запросами, регулярная серия, просрочка и приёмка. `make integration-test` нужен для поведения реальной БД; более широкие проверки — лишь при непокрытом риске.

## 4. Реализовать интерфейс и переходы

1. Заменить в `DashboardPage` развилки по `resolveUserProfile` на режимы, доступность которых следует из нового серверного ответа. Отображать единый режим рабочего стола, переключатель в общем заголовке только при доступности обоих. Счётчики и строки должны меняться вместе; загрузка, ошибка и пустое состояние не должны маскировать запрет доступа.
2. Сделать сводку кликабельной. Передавать фильтр и режим через явное состояние навигации в `App`/`AppRouter`; при открытии целевой страницы повторно запрашивать данные по её серверному scope. Обновить `AssignmentsPage` для режима «Контроль»: нынешняя логика `hasAnyAction('assign')` и `executorId` не выражает выбор режима для пользователя со смешанными правами. При необходимости добавить общий список ознакомлений с теми же режимами и фильтрами.
3. Добавить быстрые действия регистрации только для видов с `create` из текущего access summary. Учесть прекращение доступа, смену пользователя, конкурентные изменения статуса и несуществующий/уже закрытый объект при переходе из карточки.
4. Блок «Новое для меня» строить на существующем API пользовательских событий; SSE использовать как сигнал перечитать данные, включая `resync` после переподключения. События о добавлении файла добавлять отдельной серверной задачей с определёнными адресатами и повторной проверкой доступа при открытии документа. Не подменять текущие задачи историей событий.

**Проверки этапа:** компонентные тесты одиночного и смешанного режимов, отсутствия недоступных данных, переключателей и сброса при смене пользователя; тесты кликов по показателям и передачи фильтра; тесты обновления после SSE/локального изменения, ошибок и пустых состояний. Проверить сборку TypeScript и lint затронутого frontend.

## 5. Удалить устаревший путь и технические хвосты

1. После перевода всех вызовов проверить весь старый путь `DashboardPage` → `DashboardService.GetActivity` → desktop `serverclient` → `GET /api/v1/dashboard/activity` → серверный service/repository → `DashboardActivity`/`DashboardAssignmentFilter`. Удалить неиспользуемые методы, DTO, интерфейсы портов, моки, фикстуры, тестовые заглушки и старые тесты; полезные сценарии перенести на новый контракт. Если внешний API приходится сохранить, оставить один адаптер поверх новой логики и документировать срок его жизни.
2. Проверить остальные употребления `resolveUserProfile` в `App` и `ProfilePage`: убрать использование как источника доступа. Если профиль ещё нужен как чисто текстовая UX-метка, сохранить его с явно ограниченным назначением; если потребителей не осталось, удалить функцию и связанные тесты/поля. Проверить `CurrentAccessSummary`, регистрацию, sidebar и настройки на дублирующие или ставшие ненужными данные.
3. Проследить изменения до побочных эффектов: смена статуса поручения, подтверждение ознакомления, замещение, outbox, пользовательские события, SSE, read-mark и документы. Не создавать второй механизм уведомлений и не оставлять недостижимые ветки старого дашборда.
4. Проверить `rg` по старым именам и путям, diff generated bindings, HTTP-контракт, README/`docs/tech_docs.md` и план тестов. Отдельно проверить, что `docs/next-updates.md` с пользовательскими изменениями не затронут случайно.

**Результат:** один действующий путь рабочего стола; каждый сохранённый старый контракт имеет подтверждённого потребителя и указанную причину сохранения.

## 6. Итоговая приёмка

1. Сопоставить каждый показатель с результатом перехода по нему на одном и том же наборе данных. Проверить сценарии без задач, с большим числом задач, на границе суток/срока, при изменении прав и при активном замещении. Отдельно проверить, что контролёр не получает список исполнителя и наоборот без соответствующих оснований.
2. Запустить узкие Go/React-тесты изменённых пакетов и компонентов; для SQL и реальных прав — `make integration-test`. После изменения экспортируемого Wails API сгенерировать bindings штатным запуском и проверить контрактные тесты. Затем выполнить относящиеся к изменению `make frontend-lint`, `make frontend-test`, `make frontend-build`, `make go-test`/`make go-vet` по оставшимся рискам. Тяжёлые сборки и полный release gate требуются только для релизной приёмки либо конкретного риска, который не закрывают узкие проверки.
3. Составить карту покрытия для всего добавленного и изменённого кода: SQL/репозитории — интеграционные сценарии, серверные сервисы и HTTP — проверки прав и контрактов, desktop-адаптеры — контрактные тесты запросов, React-компоненты и навигация — компонентные сценарии, события/SSE — восстановление состояния после сигнала и переподключения. Для кода, который нельзя разумно проверить автоматическим тестом (например, визуальная компоновка в Wails), записать ручной сценарий и причину. Не добавлять тесты, которые лишь повторяют реализацию.
4. Провести ручной проход в desktop под пользователями из матрицы: режимы, карточки, документы, быстрые действия, свежесть данных после изменений и переподключения SSE. Сверить отсутствие прямой зависимости desktop от server и отсутствие изменений пользовательских данных/схемы без нужной миграции.
5. В итоговом отчёте указать реализованные сценарии, выполненные проверки, решения по старому API, оставшиеся ограничения и явно невыполненные проверки.

## 7. Последние документы — реализовано

Добавлена карточка четырёх последних зарегистрированных документов из разрешённой пользователю области чтения. Кнопка «Все» и общий список исключены по уточнённому требованию. Состав интерфейса, даты, серверная выборка и проверки зафиксированы в [плане раздела «Последние документы»](desktop-recent-documents-plan.md). Карточка дополняет поручения, ознакомления и ленту событий; обновление проходит через запрос разрешённой выборки и сигнал `documents` в SSE.
