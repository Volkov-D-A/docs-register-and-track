# Серверное резервирование и восстановление

Docflow создаёт согласованные копии PostgreSQL и SeaweedFS и передаёт их напрямую
на SMB. Настройки находятся в «Настройки → Резервные копии». Docker Swarm, CIFS
mount, Docker socket и привилегии root для приложения не требуются.

## Первая установка

1. Обновите сервер и примените миграцию `012_backups` через панель миграций.
2. Создайте два независимых случайных ключа вне Git: ключ шифрования настроек и
   аварийный ключ. Например, каждый ключ генерируется командой
   `openssl rand -base64 32` и записывается в отдельный защищённый файл.
3. Для Linux-контейнера файлы должны читаться UID `65532`; используйте владельца
   `65532` и режим `0400`, а каталог на хосте закройте для посторонних. Docker daemon
   должен иметь доступ к исходным файлам. Сохраните отдельную защищённую копию ключей.
4. В deployment environment задайте `DOCFLOW_SETTINGS_KEY_PATH` и
   `DOCFLOW_RECOVERY_KEY_PATH` — абсолютные пути этих файлов на Docker-хосте.
5. Подключите [Compose override](../docker-compose.backup.example.yaml):

```bash
docker compose -f docker-compose.yaml -f docker-compose.backup.example.yaml up -d --build
```

Это пример для локального Compose. В production используйте свой опубликованный
образ и сетевые настройки; recovery должен использовать ту же версию образа и
совместимые PostgreSQL tools. Исходный файл Compose secret не шифруется Docker
автоматически. Ключ настроек применяется только к SMB-паролю, не к архивам.

Постоянный volume `backup_staging` сохраняет задания и готовые локальные архивы
при перезапуске. `DOCFLOW_BACKUP_MAX_BYTES` задаёт лимит staging (по умолчанию
20 GiB); для снимка выделяется половина лимита, оставшаяся часть нужна для архива.
Контейнер содержит PostgreSQL tools 18.3. При backup major-версия `pg_dump` должна
совпадать с PostgreSQL; при обновлении БД обновляйте и runtime-образ.

## Настройка FreeNAS / SMB

В панели укажите имя или IP NAS, имя общей папки, существующий подкаталог,
пользователя и пароль. Для локальной учётной записи FreeNAS домен можно оставить
пустым. Сервер подключается к TCP 445; NAS должен быть доступен из сети контейнера.
Подкаталог создайте на NAS заранее и выдайте учётной записи права чтения, записи,
переименования и удаления только в каталоге резервирования.

Сначала сохраните настройки, затем нажмите «Проверить сохранённое подключение».
Проверка создаёт уникальный временный файл, проверяет запись, чтение, переименование
и удаление. Пароль не возвращается в API: пустое поле при сохранении оставляет
прежний пароль. Удаление пароля задаётся отдельным переключателем.

Используется SMB 2/3 с обязательной подписью сообщений, NTLM-аутентификация.
Проверен Samba-сервер с обязательным SMB encryption. Kerberos и совместимость с
конкретной версией/ACL вашего FreeNAS отдельно не подтверждены: проверка подключения
и пробное восстановление на вашем NAS остаются частью ввода в эксплуатацию.

## Создание и хранение копий

Можно запустить копию вручную или выбрать дни недели, время и IANA timezone.
При простое выполняется один пропущенный запуск, без очереди всех пропущенных дат.
Повтор одного и того же запланированного момента исключается локальным журналом.

Во время снимка сервер блокирует обычные API-запросы, дожидается текущих операций,
outbox, очистки сессий и фоновой сверки статистики. Затем создаёт dump и копирует
все объекты, проверяя наличие активных вложений. После фиксации локального комплекта
приложение возобновляет работу; упаковка, SMB-передача и проверка идут далее.
Прямые сторонние записи в PostgreSQL или S3 в это время не поддерживаются.

Формат v3 содержит `manifest.json`, `database.dump` и файлы `objects/00000000` и т. д.
Manifest хранит исходные S3-ключи, Content-Type, размеры и SHA-256 каждого объекта.
На NAS публикуются `<uuid>.tar.gz` и `<uuid>.manifest.json`. Внешний manifest
публикуется последним, после чтения и проверки архива с NAS.

«Ожидает отправки» означает, что удалённая копия ещё не готова. После сетевого сбоя
сервер сохраняет архив и повторяет передачу с увеличением интервала, до пяти попыток.
После этого доступна кнопка повторной отправки. Можно обновить пароль и повторить
отправку на то же направление. Повторная отправка начинается с начала файла.
При нехватке лимита staging новые снимки не создаются.

Очистка старых копий запускается только после успешной публикации новой. Сервер
сохраняет заданное минимальное число проверенных копий, удаляет только распознанные
комплекты старше заданного срока и не трогает чужие файлы. Скачивание для recovery
и retention координируются SMB lock-файлом. После аварийного завершения такой lock
может остаться: удаляйте его вручную только убедившись, что операция завершилась.

Журнал заданий хранится на staging volume; итоговые состояния также записываются
в `backup_jobs`, изменения настроек — в `backup_audit`. После потери staging история
панели может быть неполной; аварийная панель читает каталог непосредственно с NAS.

## Восстановление

Восстановление требует доверенного архива и пустой целевой БД/bucket. Проверка
checksum обнаруживает повреждение, но не удостоверяет происхождение архива.
Старое рабочее окружение сохраняйте до проверки восстановленных данных.

1. Остановите обычный сервер и настройте целевые PostgreSQL и S3 в deployment
   environment. БД должна уже существовать и не содержать прикладных объектов.
2. Запустите аварийный профиль. Он не требует основной БД для входа и просмотра
   каталога SMB:

```bash
docker compose -f docker-compose.yaml -f docker-compose.backup.example.yaml stop docflow-server
docker compose -f docker-compose.yaml -f docker-compose.backup.example.yaml --profile recovery up -d recovery
```

3. Откройте `http://127.0.0.1:18081` на Docker-хосте (для удалённого доступа используйте
   SSH tunnel или защищённый reverse proxy). Порт примера опубликован только на loopback.
4. Введите аварийный ключ, SMB-настройки и пароль заново, найдите копии и выберите
   комплект v3. Подтвердите восстановление словом `ВОССТАНОВИТЬ`.
5. Дождитесь успешного отчёта, остановите recovery и запустите обычный сервер.
   Для более старой схемы примените необходимые миграции через обычную панель.

Для локального архива доступна команда того же образа:

```text
docflow-server restore /restore/<uuid>.tar.gz
```

Она использует server environment и `DOCFLOW_BACKUP_DIRECTORY`. Для v2 положите
рядом исходный файл `<archive>.manifest`; имя должно сохранять вид
`backup_YYYYMMDD_HHMMSS[_NNNNNNNNN].tar.gz`. Каталог с архивами передаётся контейнеру
read-only. Архивы v1 не поддерживаются. Каталог старых v2 через SMB-панель не
перечисляется: используйте локальную команду.

До изменений проверяются архив, ограничения распаковки, dump и пустота целей.
После `pg_restore` проверяются версия/dirty схемы и ссылки на вложения; только затем
загружаются S3-объекты и сверяются их SHA-256. Общей транзакции PostgreSQL/S3 нет.
При ошибке после начала изменений файл `recovery-required` в staging блокирует
обычный запуск. Отчёт об ошибке доступен в аварийной панели/журнале. Подготовьте новую
пустую цель и повторите восстановление; не удаляйте маркер для обхода проверки.

После успешного восстановления сессии отзываются, расписание выключается. Войдите
снова, проверьте документы и скачивание вложений, затем подтвердите SMB-настройки и
включите расписание. Ключи не входят в копию: если прежний ключ настроек потерян,
подключите новый ключ и сохраните SMB-пароль заново. При ротации сначала отключите
расписание и дождитесь текущего задания; после замены ключа и перезапуска введите
пароль заново, а оставшиеся staged-копии отправьте кнопкой повторной отправки.

## Проверки и ограничения

- `make integration-test` — PostgreSQL/S3 и серверные операции.
- `make storage-smoke-test` — изолированные PostgreSQL, SeaweedFS и Samba,
  серверный backup v3, legacy v2 и новый CLI restore v2, restore v3 в пустые
  тома, проверка вложений и аварийной панели без основной БД.
- Go unit tests проверяют шифрование, архивы, расписание, барьер обслуживания и
  read-only авторизацию статуса; frontend component test проверяет сохранение
  пароля и повторную отправку.

Первый вариант делает полные копии и временно приостанавливает операции с документами.
PITR/WAL, инкрементальные копии, шифрование архивов и автоматическое переключение
production-окружения не реализованы. Измерьте длительность снимка и восстановления
на реальном объёме данных перед включением расписания.

Переходные `backup_smb_tar.sh` и `restore_smb_tar.sh` пока сохранены для проверки
старого формата; новая серверная процедура их не вызывает и не требует CIFS.
Все S3-команды этих скриптов уже выполняет серверный бинарный файл без MinIO.
