# План перехода с MinIO на SeaweedFS

Дата оценки: 9 сентября 2026 года. Статус: план, реализация не начата.

## Оценка и рекомендуемое решение

Сложность перехода **средняя в целом, низкая для прикладного кода**. Docflow использует небольшой набор стандартных S3-операций через изолированный адаптер. Рекомендуется заменить сервер хранения на SeaweedFS с S3 endpoint, сохранить `minio-go/v7` как S3 SDK и переименовать собственные типы и настройки в нейтральные `S3`/`ObjectStorage`. Название SDK не означает зависимость от сервера MinIO. Замена SDK на AWS SDK — отдельная необязательная задача, которая увеличит объём изменений без необходимости для этого перехода.

Проект в разработке: перенос объектов, сохранение старых данных, совместимость старых конфигураций и архивов, dual-write и переключение без простоя исключены. Целевой запуск — с пустыми PostgreSQL и SeaweedFS и обычным применением существующих SQL-миграций. Новые данные должны переживать перезапуск, а существующая возможность резервного копирования должна работать с новым хранилищем.

## Формат выполнения: один проход Codex

Исполнитель — Codex: он пишет код, конфигурацию и тесты, запускает проверки, исправляет обнаруженные проблемы и обновляет документацию в рамках одной задачи. Разделы ниже — последовательность работ внутри этого прохода, а не отдельные итерации с передачей пользователю. Прототип становится частью итоговых интеграционных тестов; после проверки совместимости работа продолжается до полного результата без остановки на отчёте о прототипе.

Оценка в человеко-днях для этого формата не используется. Основной объём — инфраструктура и реальные проверки S3, outbox и backup/restore; прикладные изменения остаются небольшими. Длительность зависит от доступности Docker, загрузки образов, сборок и обнаруженных несовместимостей. HA, нагрузочное проектирование и перенос исторических данных остаются вне задачи.

- Перед изменениями прочитать актуальные правила репозитория, проверить рабочее дерево и доступность Docker, Go, npm и инструментов backup/restore. Сохранить пользовательские изменения.
- Самостоятельно выбрать закреплённые версии, флаги запуска, probe и детали тестовой инфраструктуры в пределах описанной архитектуры. Не запрашивать промежуточное согласование обычных обратимых решений.
- Выполнять все изменения как один согласованный набор: Go, Compose, env, backup/restore, UI, тесты и документация должны соответствовать друг другу к завершению прохода.
- Проверять переход в отдельном Compose project на новых тестовых томах, используя сервер, собранный из текущих исходников. Не удалять существующие dev-тома для доказательства работоспособности. Процедуру сброса dev-окружения подготовить в репозитории; её выполнение над существующим стеком — только в пределах явной авторизации пользователя.
- Обнаруженные ошибки перехода исправлять в этом же проходе и повторять затронутые проверки. При внешнем препятствии продолжать независимые работы; обязательные разрешения среды запрашивать через штатный механизм.
- Отмечать выполненные пункты этого документа по фактическому результату. Для заблокированных проверок указать команду, причину и оставшуюся проверку; не считать их успешно пройденными.
- Завершить задачу сводкой изменений, результатов проверок и ограничений. Коммит, публикация образа и развёртывание не являются обязательными шагами этого прохода без соответствующего запроса.

Этот документ задаёт будущую реализацию. Текущая задача — только адаптация плана; реализация перехода ещё не запускалась.

## Совместимость и целевая схема

SeaweedFS документирует поддержку используемых bucket/object операций, ListObjectsV2 и multipart upload. Его S3 gateway обращается к Filer; доступны объединённые режимы запуска. Есть отличия от S3 в семантике каталогов и удаления, поэтому UUID-ключи следует сохранить. Это основание ожидать небольшой объём изменений адаптера, но не доказательство совместимости конкретной пары версий. [Официальная матрица S3 API](https://github.com/seaweedfs/seaweedfs/wiki/Amazon-S3-API).

```text
Desktop → HTTP API docflow-server → S3 SDK → SeaweedFS S3 gateway
                       │                       │
                       └→ PostgreSQL           └→ Filer → Volume server
                                                        ↑ Master
```

Для dev и первоначального одноузлового развёртывания выбрать `weed mini -dir=/data`, с явно заданным S3-портом 8333, постоянным томом и закреплённым тегом/ digest образа. Он объединяет необходимые компоненты; значения по умолчанию могут меняться между версиями. HA требует отдельного проектирования компонентов и quorum, поэтому в данный переход не включается. [Официальный Quick Start](https://github.com/seaweedfs/seaweedfs/wiki/Quick-Start-with-weed-mini).

Endpoint внутри Compose планируется как `http://seaweedfs:8333`. Master, Filer, Volume и административные интерфейсы не публиковать в пользовательскую сеть. HTTP API приложения остаётся единственным путём работы desktop с вложениями. Постоянный том должен охватывать и объекты, и метаданные SeaweedFS; состав каталогов проверить для выбранного образа.

Аутентификацию задавать явно. SeaweedFS поддерживает файл identities/credentials и AWS-переменные окружения; приоритет источников имеет значение. Использовать один выбранный способ, а для dev можно передать `S3_ACCESS_KEY_ID`/`S3_SECRET_ACCESS_KEY` из окружения Compose как `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` контейнера. Production-настройки хранить как runtime secrets; проверить отказ анонимным и неверно подписанным запросам. [Официальные настройки credentials](https://github.com/seaweedfs/seaweedfs/wiki/S3-Credentials).

## Порядок реализации

### 1. Зафиксировать версию и доказать совместимость

- [ ] Выбрать конкретный релиз SeaweedFS, закрепить образ; проверить команды и флаги по `weed mini -help` именно этого образа. Не использовать `latest`.
- [ ] Поднять изолированный экземпляр, проверить текущий `minio-go/v7 v7.3.0` из go.mod без смены SDK.
- [ ] Проверить создание и повторную проверку bucket, upload/download с совпадением SHA-256 и Content-Type, удаление, listing, отсутствие объекта.
- [ ] Проверить подпись V4, определение региона SDK, path-style адресацию. При необходимости явно задать регион/path-style в адаптере и добавить тесты.
- [ ] Проверить большой файл с реальным multipart, checksum-заголовки и отмену upload. Порог multipart определить по используемой версии SDK; небольшой файл этот путь не проверяет.

Результат шага: закреплённая пара SeaweedFS/SDK и воспроизводимая проверка операций, включённая в итоговый набор тестов. Сразу продолжить реализацию следующих шагов. При несовместимости проверить настройки и другой закреплённый релиз в этом же проходе; если выбранный SDK остаётся препятствием, зафиксировать конкретную ошибку и обоснование необходимого изменения клиента.

### 2. Обновить конфигурацию и инфраструктуру

- [ ] В обоих Compose заменить MinIO на SeaweedFS; заменить переменную версии в `.envExample`, создать новый том, обновить зависимости и комментарии Makefile.
- [ ] Ввести `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_BUCKET`, `S3_USE_SSL`; согласованно обновить Go, Compose, примеры и backup env. Старые `MINIO_*` aliases не нужны.
- [ ] Сохранить разбор endpoint с HTTP(S), явно определить приоритет схемы URL над SSL-флагом и проверить конфликтующие значения тестом: текущая загрузка применяет bool после URL.
- [ ] Сохранить создание bucket приложением для первого запуска, учесть соответствующее право identity. Read-only healthcheck bucket не создаёт.
- [ ] Добавить готовность SeaweedFS и ожидание её сервером. Проверка TCP недостаточна: проверить доступность S3 и отдельно возможность чтения/записи. Pre-start probe не должен требовать bucket, который создаёт ещё не запущенный docflow-server. Проверить наличие инструмента probe в образе или добавить отдельный init/probe сервис.
- [ ] Проверить холодный старт, повторный старт и рестарт контейнера с сохранением созданных тестовых объектов.
- [ ] Для проверки собирать сервер из текущих исходников через отдельный Compose override; не принять скачанный старый образ за результат изменений.

### 3. Убрать привязку прикладного кода к названию продукта

- [ ] Переименовать `MinioConfig` в `S3Config`, `MinioService` в `S3Storage`, конструктор и healthcheck; обновить DI, валидацию и тесты. `internal/storage/minio.go` переименовать в `s3.go`.
- [ ] Сохранить интерфейсы хранения, streaming, ограничения размера, context cancellation и таймауты; корректировать поведение только по результатам проверок.
- [ ] В UI и сообщениях использовать «объектное хранилище» или «хранилище вложений». Обновить `StorageTab.tsx`, `SystemStatisticsTab.tsx`, `MigrationsTab.tsx` и `internal/desktop/services/settings.go`.
- [ ] Не менять SQL-схему, object keys, outbox-события и API только из-за смены провайдера. Не переписывать исторические миграции ради комментариев.

### 4. Добавить интеграционные проверки реального хранилища

- [ ] Расширить изолированный integration Compose сервисом SeaweedFS и тестовыми credentials; настроить endpoint из окружения, отдельные bucket/тома, ожидание готовности и очистку через trap.
- [ ] Обновить `make integration-test`, чтобы S3-тесты действительно запускались, а не пропускались из-за отсутствия env; ручной узкий запуск должен понятно сообщать о пропуске.
- [ ] Покрыть multipart, отмену, неверные credentials, отсутствующий bucket/object, повторный delete, listing более 1000 объектов с пагинацией и точный подсчёт байтов/объектов.
- [ ] Проверить на реальных PostgreSQL и SeaweedFS: upload → download → delete; retry `attachment_delete` после недоступности S3; повторную доставку; компенсацию при сбое записи metadata; missing/orphan reconciliation; координацию статистики с upload/delete.
- [ ] Проверить восстановление доступности после остановки/старта SeaweedFS и завершение запросов по timeout. Статистика отражает логический размер объектов, а не физическое занятие диска SeaweedFS.

### 5. Сохранить работоспособность backup/restore для новых данных

Это проверка существующей функции проекта после перехода, а не миграция старого MinIO.

- [ ] На первом переходе оставить `mc` как S3 CLI, закрепить его версию и проверить `alias`, `mb`, `ls`, `mirror` против SeaweedFS. Административные команды MinIO не использовать. Полное удаление SDK/CLI MinIO из зависимостей не является целью.
- [ ] Обновить env allowlist, названия каталога архива и поля manifest на `objects/` и `s3_bucket`, повысить версию формата и синхронно изменить reader/writer. Поддержка старых архивов не требуется.
- [ ] Устранить передачу credentials через интерполяцию в shell-команду: использовать защищённую конфигурацию клиента и корректное quoting.
- [ ] Определить доступ backup-контейнера к S3: текущие скрипты используют `--network host`, а Compose не публикует S3. Предпочесть подключение контейнера к сети Compose и внутренний endpoint; не использовать `localhost` другого контейнера.
- [ ] На время согласованной копии остановить записи приложения и outbox, сохранив доступ к PostgreSQL/S3. Сохранить manifest, checksum и атомарную публикацию архива.
- [ ] Проверить restore свежей копии в пустой тестовый стек: сначала PostgreSQL и его валидация, затем объекты; при ошибке PostgreSQL восстановление объектов не запускается. Сравнить содержимое и reconciliation после восстановления.

Логический S3 backup позволяет восстановить объекты в заново созданный SeaweedFS. Копирование только файлов Volume server не заменяет такой backup и не должно вводиться как упрощённый способ восстановления.

### 6. Проверить чистый запуск и завершить документацию

- [ ] В изолированном Compose project запустить пустые PostgreSQL и SeaweedFS, применить обычные миграции и создать тестовые данные. Проверить готовность сервера и полный сценарий вложений из текущей сборки. Подготовить процедуру переключения dev-стека, которая не оставляет metadata старых вложений и pending outbox рядом с пустым bucket.
- [ ] Сброс ограничить нужными dev-томами. Текущий `make storage-reset` выполняет общий `down -v`, поэтому для перехода подготовить явную процедуру, учитывающую Seq и Caddy.
- [ ] Обновить README, tech_docs, AGENTS.md, актуальные deployment/release-инструкции и затронутые тесты backup/release tooling. Исторические документы в архиве можно сохранить как историю.
- [ ] Выполнить `make go-test`, `make go-vet`, `make integration-test`, frontend lint/test/build для изменённых текстов и `make docs-links-check`. Проверить desktop-сценарий вложений на Linux и Windows; при недоступной платформе явно зафиксировать непроверенный сценарий.
- [ ] Проверить `docker compose config` для обоих Compose с тестовыми env без вывода настоящих secrets. Сохранить результат тестового restore. `make release-gate` относится к последующей подготовке выпуска и не заменяет перечисленные проверки текущего прохода.

## Критерии завершения и риски

Переход завершён, когда пустой стек воспроизводимо запускается, все операции вложений и сверки проходят с SeaweedFS, outbox переживает недоступность S3, новые объекты сохраняются после рестарта, backup/restore проверен, а активные конфигурации и UI соответствуют новому хранилищу. Остаточные `minio-go` и `mc` допустимы как совместимые S3-клиенты.

| Риск | Как закрыть |
| --- | --- |
| Различия multipart, подписи, checksum и ошибок | Проверки точной пары версий на шаге 1 и исправление несовместимостей в этом же проходе |
| Процесс запущен, но storage ещё не готов | Readiness, отсутствие циклической зависимости bucket/init, холодный старт |
| Неполный listing или отличие семантики удаления | Пагинация, повторный delete, сохранение UUID-ключей |
| Потеря новых данных после рестарта | Постоянные данные и метаданные, тест перезапуска и restore |
| Рабочее приложение, но сломанные backup-скрипты | Отдельный этап backup/restore и доступ из сети контейнера |
| Неожиданный рост эксплуатационной сложности | Одноузловая схема на первом этапе; HA и capacity planning отдельно |

Если проверка перехода не проходит, Codex исправляет причину в текущем проходе. Если завершение блокирует внешняя среда, в итоговом отчёте явно указывается, какая часть реализации готова и что остаётся неподтверждённым. Один проход не означает допустимость пропуска проверок или объявления частичного результата завершённым переходом.

Для возможного последующего отката dev-окружения подготовить инструкцию возврата к предыдущему коду/Compose с пустыми MinIO и PostgreSQL. Автоматически откатывать пользовательские изменения не требуется. Сохранение данных между вариантами не планируется. В рамках подготовки этого документа контейнеры, данные и конфигурация приложения не изменялись.
