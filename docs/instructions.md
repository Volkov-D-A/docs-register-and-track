# Эксплуатация SeaweedFS

Docflow использует SeaweedFS **4.46** и AWS SDK for Go v2. Проверку готовности,
экспорт и импорт выполняет `docflow-server storage`; отдельный S3 CLI не нужен.
[Релиз SeaweedFS](https://github.com/seaweedfs/seaweedfs/releases/tag/4.46)
и [описание mini](https://github.com/seaweedfs/seaweedfs/wiki/Quick-Start-with-weed-mini).

`weed mini -dir=/data -s3.port=8333` хранит данные и метаданные в одном постоянном
томе `seaweedfs_data`. Внутренний endpoint — `http://seaweedfs:8333`. Порты Master,
Filer, Volume, WebDAV, Admin и S3 не публикуются в пользовательскую сеть.
Desktop работает с HTTP API Docflow. Одноузловой пример не обеспечивает HA.

В проекте три Compose-файла: `docker-compose.yaml` для dev,
`docs/examples/docker-compose.prod.example.yaml` для production и `testing/compose/integration.yaml`
для тестов. В последнем профиль `smoke` дополнительно включает сервер;
обычные интеграционные тесты запускают только PostgreSQL, SeaweedFS и S3 probe.

## Конфигурация и первый запуск

Скопируйте [.envExample](examples/.envExample) в новый `.env` и задайте `S3_ENDPOINT`,
`S3_ACCESS_KEY_ID`, `S3_SECRET_KEY_FILE_PATH`, `S3_BUCKET` и при необходимости
`S3_USE_SSL`. Схема `http://` или `https://` имеет приоритет над SSL-флагом.
Переменные `MINIO_*` больше не читаются. SDK использует Static V4,
регион `us-east-1` и path-style URL.

SeaweedFS получает credentials через `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`.
Не задавайте одновременно альтернативные identities-файлы или `S3_BUCKET`
самому SeaweedFS: bucket приложения создаёт сервер. `s3-ready` проверяет S3v4,
создание временного bucket, запись, чтение и удаление до запуска приложения.
Read-only проверка приложения никогда не создаёт bucket.

В dev и [production Compose](examples/docker-compose.prod.example.yaml):
`S3_ACCESS_KEY_ID` задаёт логин в `.env`, а `S3_SECRET_KEY_FILE_PATH` указывает
на внешний файл с секретным ключом. Он монтируется в `/run/secrets`; сервер
читает его через `S3_SECRET_ACCESS_KEY_FILE`. Не задавайте одновременно
секрет и его `_FILE`. Учтите доступ на чтение для UID 65532 сервера: локальные
Compose file secrets сохраняют права исходного файла. Храните их вне Git,
в закрытом каталоге; настройте владельца/ACL для runtime пользователя.

Оба стека используют опубликованный образ сервера из Docker Hub. Запуск dev:

```bash
make storage-up
```

## Переход dev на пустые данные

Перенос старых объектов, metadata и outbox не выполняется. Нельзя подключать
старую PostgreSQL к пустому SeaweedFS. Перед сбросом остановите работу клиентов,
сохраните нужные внешние данные и проверьте Compose project.

1. Обновите код и `.env` по новому примеру.
2. Просмотрите точный список томов: `bash scripts/reset-dev-storage.sh`.
3. Для намеренного удаления dev-данных выполните `make storage-reset`.

Скрипт выбирает только тома текущего Compose project с labels `pgdata`,
`seaweedfs_data`, затем собирает текущий сервер из основного Compose и запускает чистый стек. Seq и Caddy volumes
сохраняются. Пустая БД получает обычные embedded migrations. Скрипт сброса
**не выполняется** интеграционными тестами.

# Серверное резервирование и восстановление

Docflow создаёт согласованные копии PostgreSQL и SeaweedFS и передаёт их напрямую
на SMB. Администратор управляет копиями в «Настройки → Резервные копии» обычного
приложения. Desktop обращается только к HTTP API сервера.

## Установка

1. Обновите сервер и примените миграции, включая `012_backups`.
2. Создайте ключ шифрования SMB-пароля вне Git: `openssl rand -base64 32`.
   Сохраните результат в защищённом файле и сделайте отдельную защищённую копию.
3. Файл в Linux-контейнере должен читаться UID `65532`. Используйте владельца
   `65532`, режим `0400` и закрытый каталог на хосте.
4. Задайте `DOCFLOW_SETTINGS_KEY_PATH` — абсолютный путь файла на Docker-хосте.
   Настройки резервирования встроены в [dev Compose](../docker-compose.yaml) и
   [production Compose](examples/docker-compose.prod.example.yaml). Запустите нужный стек:

```bash
# Dev
docker compose up -d
# Production (из корня репозитория; .env и caddy/ находятся там же)
docker compose --project-directory . --env-file .env -f docs/examples/docker-compose.prod.example.yaml up -d
```

В production используйте опубликованный образ и настройки своего окружения.
Ключ шифрует сохранённый SMB-пароль; сами архивы не шифруются. Отдельный аварийный
ключ, recovery-порт и recovery-сервис не нужны. Команды `recovery` и `restore`
удалены; служебные команды `storage` сохранены.

Постоянный volume `backup_staging` хранит локальные архивы и журналы. Не размещайте
его на временной файловой системе. `DOCFLOW_BACKUP_MAX_BYTES` задаёт бюджет staging
(по умолчанию 20 GiB). Для резервирования используется до половины бюджета.
При восстановлении для каждого распакованного комплекта выделяется до одной
восьмой бюджета: одновременно хранятся источник, распакованные данные и проверенная
страховочная копия. Увеличьте бюджет и диск для крупных архивов. Перед операцией
проверяются занятый бюджет и свободное место; сохранённые архивы автоматически
не вытесняются ради нового задания.

Серверный образ содержит PostgreSQL tools. Major-версия `pg_dump` должна совпадать
с PostgreSQL; при обновлении БД обновляйте runtime-образ.

## SMB и создание копий

Укажите сервер NAS, общую папку, существующий подкаталог, пользователя, домен при
необходимости и пароль. Сервер должен иметь сетевой доступ к NAS и права чтения,
записи, переименования и удаления внутри выбранной папки. Используются SMB 2/3
и обязательная подпись сообщений; kernel mount и Docker socket приложению не нужны.

Сохраните настройки и нажмите «Проверить сохранённое подключение». Проверка
выполняет реальные файловые операции с временным файлом. Пустое поле пароля
сохраняет прежний пароль; для очистки есть отдельный переключатель.

Копию можно создать вручную или по расписанию с IANA timezone. После простоя
выполняется один пропущенный запуск. На время снимка сервер останавливает приём
обычных запросов, дожидается запросов и фоновых записей. Передача на SMB происходит
после возобновления работы. Готовый v3-комплект:

- `<uuid>.tar.gz` — dump, manifest и объекты с контрольными суммами;
- `<uuid>.manifest.json` — размер и SHA-256 архива, ID и дата.

Внешний manifest публикуется последним после проверки чтением с NAS. При ошибках
передачи staged-архив сохраняется; доступны автоматические попытки и ручной повтор
на исходное SMB-направление. Изменение настроек не перенаправляет уже созданное задание.

## Каталог и проверка

Каталог читает SMB независимо от локальной истории, поэтому работает после сброса
БД и потери staging. В нём видны ID, дата, размер, неполные комплекты и состояние
проверки. Наличие manifest и совпадение размера не считаются полной проверкой.
«Проверен» означает последнюю успешную полную проверку данного комплекта; при
восстановлении и удалении необходимые проверки выполняются снова.

«Проверить» скачивает комплект, сверяет SHA-256, безопасно распаковывает его с
ограничениями размера, проверяет dump и версию схемы. Для v2 нужны исходные файлы
`backup_YYYYMMDD_HHMMSS[_NNNNNNNNN].tar.gz` и `<archive>.manifest` в той же папке SMB.
Дата v2 берётся из имени. Локальный старый архив оператор предварительно размещает
на SMB. V1 не поддерживается; ручное удаление v2 через панель не предусмотрено.

## Восстановление через админпанель

1. Выберите копию и нажмите «Восстановить».
2. Выполните проверку выбранного комплекта.
3. Убедитесь, что знаете пароль пользователя из архива. Проверьте ID и дату,
   подтвердите замену текущих данных и нажмите «Заменить данные».
4. Дождитесь результата. После успеха выйдите и войдите учётной записью из архива,
   проверьте документы и скачивание вложений.
5. Сохраните SMB-пароль заново и явно включите расписание.

Заменяются документы, файлы, пользователи, права и настройки. Поддерживаются только
выделенные БД и bucket Docflow. Общие цели с посторонними таблицами, функциями или
файлами не поддерживаются. Другие БД и bucket не удаляются.

До замены сервер создаёт и проверяет локальную страховочную копию текущих данных.
При её ошибке замена не начинается. Затем он очищает прикладную схему и выбранный
bucket, восстанавливает dump и объекты, проверяет вложения и checksum, применяет
поддерживаемые миграции. PostgreSQL и S3 не объединены в атомарную транзакцию.
После успеха все сессии отзываются, расписание выключается и восстановленный
SMB-пароль очищается: ключ шифрования может отличаться от исходного.

Фоновые операции продолжаются после закрытия окна. Отмена доступна при скачивании
и проверке; во время замены она запрещена. Наблюдение использует случайный токен
только для чтения одного задания, сроком 12 часов. Токен хранится в памяти клиента,
передаётся в заголовке Authorization, не помещается в URL. На сервере в защищённом
журнале сохраняются только хеш и срок. Токен не позволяет выполнять другие действия.
После закрытия приложения или истечения срока анонимного доступа к статусу нет.

## Сбои и восстановление после потери БД

Каждая опасная фаза фиксируется в `<job-id>.operation.json` на staging. Источник
сохраняется в каталоге задания проверки, страховочная копия — в каталоге задания
восстановления (`safety.tar.gz`). Они сохраняются при сбое; берегите staging как
данные приложения и закрывайте доступ посторонним.

При ошибке после начала замены сервер пытается вернуть страховочную копию.
Если откат не удался, файл `recovery-required` блокирует бизнес-API, в том числе
после перезапуска. На обычном HTTP-порту остаётся только чтение статуса с ранее
выданным действующим токеном. Отдельного интерфейса восстановления нет.

Если БД неисправна или откат не удался:

1. Остановите целевой сервер. Сохраните staging, журналы и доступ к исходной копии SMB.
2. Сбросьте только выделенные БД и файловое хранилище Docflow в целевом окружении.
   Определите имена томов по Compose-конфигурации; не удаляйте посторонние тома.
   Нельзя сохранять старые объекты SeaweedFS при сбросе одной БД.
3. Подключите новый пустой staging, сохранив прежний отдельно для диагностики.
   Не удаляйте маркер ради запуска поверх частично восстановленных данных.
4. Запустите обычное приложение, выполните начальную настройку администратора,
   сохраните доступ к SMB и восстановите копию через описанный мастер.

После успеха и проверки данных оператор может архивировать либо удалить более
не нужные локальные staging-комплекты при остановленных заданиях. Ручное удаление
копии в панели затрагивает только SMB, а не локальные архивы.

## Удаление и retention

«Удалить» требует подтверждения ID, даты и размера v3-копии. Общая SMB-блокировка
сериализует проверку, восстановление и retention. Удаление повторно проверяет
manifest и сохраняет минимум полностью проверенных остальных комплектов;
последняя проверенная копия защищена даже при минимуме 1.

Промежуточный `<uuid>.delete.json` фиксирует начатое удаление. При сетевом сбое
комплект отображается как незавершённое удаление. Повторите операцию после
восстановления SMB; уже отсутствующие части не мешают завершить удаление.
Открытый lock-файл защищён от удаления другим клиентом. После разрыва SMB-сессии
блокировка может быть получена заново без ручного удаления lock-файла.

История сохраняется в staging, включая инициатора, ID, результат и ошибку.
У созданной локально копии появляется состояние «Удалено с SMB». Автоматический
retention использует тот же механизм защиты минимума и удаления.

## Проверки

- `make go-test`, `make go-vet` — архивы, токены, права, отмена, фазы замены и откат.
- `make integration-test` — изолированные PostgreSQL/S3, сервер и lifetime lease.
- `make storage-smoke-test` — реальный Samba и собранный сервер: создание v3,
  замена непустой цели, восстановление v3/v2 после полного сброса, отзыв сессий,
  чтение вложений, защита минимума и удаление без старой локальной истории.
- `make frontend-lint`, `make frontend-test`, `make frontend-build` — интерфейс,
  в том числе обязательная проверка и подтверждение перед заменой.

Совместимость с конкретными NAS/ACL, обрывы сети, заполнение диска и RPO/RTO
проверяйте на целевом окружении. Desktop-сценарии на Linux и Windows требуют
отдельной проверки; API smoke не заменяет проверку GUI.
PITR/WAL, инкрементальные копии и шифрование архивов не реализованы.


## Обновление состояния в desktop

История заданий обновляется по SSE-событиям сервера. Проверка, удаление и
восстановление используют отдельное соединение с токеном наблюдения конкретного
задания; оно продолжает работать при замене БД и завершении обычной сессии.
После разрыва соединение восстанавливается автоматически и получает текущее
состояние. Открытие вкладки также загружает актуальные данные. Для изменений
каталога SMB, сделанных вне Docflow, используйте «Обновить каталог».
Для использования событий необходимо обновить и сервер, и desktop.
