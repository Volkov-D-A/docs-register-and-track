# План внутренней версии сборки клиента и сервера

Статус: предложение к реализации. Изменения поведения пока не внесены.

## Задача и текущее поведение

Публичная версия остаётся `1.0.7`. Для определения соответствия desktop и сервера вводится автоматически вычисляемая внутренняя версия, например `1.0.7.213`. В пользовательском интерфейсе она отображается только в системной статистике.

Сейчас `internal/server/system.go` сравнивает точное равенство трёх компонентов релизной версии. Desktop получает версию из `releaseassets.CurrentVersion()` и вызывает `/api/v1/system/compatibility` через `SystemService.GetBootstrapStatus()` перед входом. Разные сборки одного релиза проходят эту проверку. Источник публичной версии — `docs/releases.yaml`, из которого генерируются `internal/releaseassets/current_release.yaml` и версия в `wails.json`.

## Предлагаемая схема

Разделить публичную версию и метаданные сборки:

| Поле | Назначение |
| --- | --- |
| `releaseVersion` | Публичная версия `1.0.7`, существующий источник сохраняется |
| `buildNumber` | Число коммитов, достижимых из HEAD: `git rev-list --count HEAD` |
| `sourceRevision` | Полный SHA коммита для однозначного сравнения веток |
| `sourceFingerprint` | Для локальной разработки: отпечаток исходников с незакоммиченными изменениями |
| `dirty` | Признак сборки из изменённого рабочего дерева |
| `buildVersion` | Представление `releaseVersion.buildNumber` для системной статистики |

Номер относится к состоянию исходников, а не к каждому запуску компилятора. Повторные сборки одного коммита на Linux и Windows получают одинаковые значения. Не нужны ручное увеличение файла-счётчика, отдельный сервер нумерации или общий счётчик запусков CI. Номер не сбрасывается при смене релиза. В текущем checkout число коммитов равно 362; пример `213` не является предлагаемым начальным значением.

Количество коммитов не уникально между ветками и может меняться при переписывании истории. Поэтому проверять только четвёртый компонент недостаточно: для чистых сборок сравнивать одновременно публичную версию, номер и полный SHA. Номер не использовать для определения, какая из двух разных веток «новее».

Это строгая проверка соответствия исходников: даже совместимое изменение или коммит документации потребует согласованной пары сборок. Это осознанное исходное правило. Если потребуется разрешать разные сборки, отдельно проектировать версию протокола совместимости; автоматически вывести совместимость API из номера коммита нельзя.

## Автоматизация сборки

1. Добавить общий пакет `internal/buildinfo` и генератор метаданных в `tools`. Передавать значения в Go-бинарники через `-ldflags -X`. Публичную версию продолжать читать существующим способом; четырёхкомпонентную строку не передавать существующему парсеру релизной версии.
2. Подключить генератор к `make dev`, `make build-linux`, `make build-windows`, сборке и публикации сервера. Предусмотреть отдельную цель сборки серверного бинарника. Один алгоритм должен обслуживать все пути сборки и не требовать ручной правки `.env` для внутреннего номера.
3. Вычислять метаданные до Docker build и передавать через build arguments в стадию компиляции: `.git` уже исключён из Docker context. Проверять обязательные значения внутри сборки образа. Сейчас аргумент `VERSION` используется только в OCI label и не задаёт идентификатор бинарника.
4. Для распространяемых сборок требовать чистое дерево и полную Git-историю. Shallow checkout должен приводить к понятной ошибке с требованием получить историю. Сборку из архива без `.git` разрешать только с заранее созданным манифестом метаданных, соответствующим этому архиву. Не подставлять молча `0`, `unknown` или текущую дату.
5. Для локального `make dev` разрешить dirty-дерево, но включать в проверку детерминированный отпечаток исходников. Определить единый набор файлов для desktop и сервера: отслеживаемые исходники и новые неигнорируемые файлы, влияющие на сборку; исключить `.git`, секреты, локальные настройки, артефакты и генерируемые bindings. Хешировать отсортированные пути и содержимое с нормализацией LF для текстовых файлов, учитывать удаления. Набор исключений хранить централизованно. Пересчитывать отпечаток при пересборке backend в Wails dev; однократного вычисления при старте недостаточно. Если этот путь пока не реализован, dirty-сборку отклонять, а не считать эквивалентной HEAD.
6. Прямые `go run` / `go build` без метаданных считать неопознанными сборками: не разрешать положительный результат проверки совместимости даже между двумя такими бинарниками. Служебные команды, которым идентификация сборки не нужна, например существующая `version`, должны продолжать работать.
7. Для dev-образов добавить неизменяемый тег с публичной версией, номером и SHA; проверять, что тег и встроенные данные согласованы. Оставить публичные релизные обозначения трёхкомпонентными. Настроить выбор конкретного dev-образа в Compose, чтобы повторно используемый релизный тег не подменял ожидаемую сборку.

## Проверка при подключении

Расширить существующий контракт compatibility отдельными полями идентификации сборки и признаком версии протокола проверки. `clientVersion`, `serverVersion`, минимальная и максимальная релизные версии сохраняют нынешний смысл.

Правила проверки:

- Разные публичные версии: существующие `client_too_old` / `client_too_new`.
- Одинаковая публичная версия, но разные номер, SHA, dirty-статус или отпечаток dirty-исходников: `build_mismatch`, вход блокируется.
- Нет обязательной идентификации: `build_identity_required`; некорректный формат полей: HTTP 400 с отдельным кодом ошибки.
- Для чистых сборок совпадают версия, номер и SHA: совместимы. Для dirty-сборок дополнительно требуются dirty-статус обеих сторон и одинаковый отпечаток.
- Новый клиент самостоятельно проверяет наличие поддерживаемой версии протокола и идентификации в ответе. Ответ старого сервера `compatible: true` без новых полей не считается успешным.

На экране подключения показывать сообщение «Сборки приложения и сервера не соответствуют друг другу. Обратитесь к администратору для установки согласованных сборок». Внутренний номер и SHA туда не выводить; публичную версию можно оставить. Передача метаданных по API необходима для проверки и не является их отображением пользователю.

Сохранить текущую область действия: проверка официальным desktop перед входом. Она не является серверным запретом запросов от произвольного HTTP-клиента. Постоянный контроль уже открытой сессии после замены сервера — отдельное расширение, не включённое в этот план.

## Системная статистика

- Дополнить серверную диагностику и `SystemServiceStatistics` метаданными сервера.
- В desktop-адаптере статистики добавить локальные метаданные клиента: сервер не должен определять их вместо клиента.
- В `SystemStatisticsTab.tsx` показывать «Сборка клиента» и «Сборка сервера» в формате `1.0.7.362`; рядом диагностические SHA и признак локальных изменений при необходимости.
- Сохранить публичную версию в окне «О программе», release notes, заголовках, метаданных приложения и обычных сообщениях.
- Обновить Wails bindings штатной сборкой после изменения экспортируемых моделей.

При несовместимости вход заблокирован, поэтому статистика в этом клиенте недоступна. Диагностику идентичности сборок администратор получает из метаданных артефактов и технического API; отдельный экран с внутренними номерами перед входом не добавляется.

## Внедрение

1. Реализовать пакет метаданных и все пути сборки, включая dev и Docker.
2. Добавить поля DTO, серверную проверку и обязательную проверку ответа в desktop.
3. Добавить отображение в статистике, обновить bindings и инструкции сборки.
4. Выпустить согласованную пару клиента и сервера из одного чистого коммита. Старый клиент с новым сервером и новый клиент со старым сервером должны получать отказ. Не предусматривать скрытый откат к сравнению только релиза.
5. На первом внедрении согласовать обновление обеих сторон; при откате возвращать пару артефактов. Миграция БД для метаданных бинарников не требуется.

## Проверки при реализации

- Генератор: повторяемость, разные ветки с одинаковым номером, shallow checkout, отсутствие Git, dirty-файлы и удаления, одинаковые исходники при LF/CRLF, отсутствие влияния артефактов и секретов.
- Compatibility: совпадающие сборки, разные релизы, разные номера, одинаковые номера при разных SHA, dirty-пары, отсутствующие и некорректные данные.
- Desktop: старый сервер не проходит новую проверку; несовпадение блокирует вход; отсутствие номера в пользовательском сообщении.
- Frontend: обе внутренние версии отображаются только в системной статистике, окно «О программе» сохраняет публичную версию.
- Один проверочный комплект Linux/Windows desktop и Docker server из одного коммита: встроенные метаданные совпадают. Проверить, что изменение backend при `make dev` обновляет отпечаток.
- Запускать узкие тесты изменённых пакетов; сборки нужны для проверки передачи метаданных и генерации bindings. Интеграционные тесты БД для этой задачи не требуются.

Критерий готовности: разные исходники в пределах одного релиза больше не проходят проверку, повторная сборка одних исходников остаётся совместимой, внутренние номера не требуют ручного назначения и отображаются только в системной статистике.
