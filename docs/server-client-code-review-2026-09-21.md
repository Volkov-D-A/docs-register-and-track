Код-ревью сервера и клиента Docflow, 21 сентября 2026

Проверены HTTP-аутентификация и авторизация, операции с документами и вложениями, SQL-репозитории, outbox, резервное копирование, desktop HTTP-адаптеры, работа с локальными файлами, React-состояние и тестовые контракты. Это статическое ревью с запуском существующих тестов и четырьмя дополнительными диагностическими проверками. Продуктовый код не изменён.

Приоритеты: **P1** — исправить прежде всего: нарушение ограничений доступа или защиты; **P2** — значимая ошибка поведения, надёжности или тестирования; **P3** — сопровождение и удаление лишнего кода. Подтверждение по коду не означает, что выполнена эксплуатация против работающего сервера.

**Сервер: замечания в порядке приоритета**

1. **P1. Маршрут загрузки в документ обходит ограничения файлов исполнения.**

   Место: [attachment_server.go](../internal/server/services/attachment_server.go), строки 200–213; [assignment_repo.go](../internal/server/repository/assignment_repo.go), строки 495–510.

   При включённом `assignment_completion_attachments_enabled` пользователь без права `upload` может вызвать `POST /api/v1/documents/{id}/attachments`. Достаточно, чтобы `HasDocumentAccess` нашёл его исполнителем или соисполнителем любого поручения документа. SQL не проверяет статус, текущую итерацию серии или право действовать от имени основного исполнителя. Вложение сохраняется без `assignment_id`.

   При этом маршрут `/assignments/{id}/attachments` требует основного исполнителя/замещающего, текущую итерацию и, для пользователя без прямого `upload`, статус `in_progress`. Поэтому ограничения обходятся выбором другого HTTP-маршрута. В частности, сохраняется возможность загрузки после завершения поручения и через историческую итерацию.

   Подтверждение: дополнительная проверка вызвала `UploadContent` без права `upload`; операция прошла, чтения состояния поручения не было. SQL-предикат проверен отдельно по коду.

   Исправление: для document upload требовать прямое право `upload`; исключение для исполнителя оставить в assignment upload с привязкой к поручению и транзакционной проверкой его состояния. Недостающие тесты: одна матрица прав для обоих маршрутов, включая соисполнителя, завершённое поручение и историческую итерацию.

2. **P1. При заполнении таблицы неудачных аутентификаций ограничитель начинает пропускать новые ключи без ограничений.**

   Место: [management.go](../internal/server/management.go), строки 591–625.

   Таблица ограничена 4096 ключами `IP + login`. Когда она заполнена неистёкшими записями, `recordAuthenticationFailure` просто возвращается для нового ключа. `authenticationAllowed` разрешает запросы для отсутствующего ключа. Новые неудачи не учитываются, повторные попытки продолжают проходить.

   Это особенно существенно для Basic Auth миграций: этот путь не увеличивает постоянный счётчик неудач пользователя в БД. На обычном login ограничение в БД остаётся, поэтому утверждение о полном отключении всех механизмов защиты было бы неверным. Заполнение таблицы требует достаточно интенсивного потока разных логинов; диагностическая проверка воспроизводила уже заполненное состояние, а не сетевую атаку.

   Подтверждение: после заполнения таблицы дополнительная проверка записала десять неудач нового ключа, и он по-прежнему был разрешён.

   Исправление: ограничение по источнику/общему бюджету и безопасное поведение при исчерпании ёмкости; учитывать попытку до дорогой проверки пароля. Тестировать также одновременные запросы и все три пути аутентификации.

3. **P2. Миграции принимают пароль, просроченный по `password_lifetime_days`.**

   Место: [management.go](../internal/server/management.go), строка 576; [auth.go](../internal/server/auth.go), строки 379–392.

   Обычный login вызывает `passwordChangeRequired`, учитывающий возраст пароля и настройку срока действия. `authenticateAdmin` проверяет только сохранённый флаг `PasswordChangeRequired`. Для активного администратора с просроченным паролем и флагом `false` вход запрещён, а Basic Auth для применения/отката миграций разрешён.

   Подтверждение: отдельная проверка с паролем возрастом 30 дней и сроком действия один день получила `passwordChangeRequired == true` и успешную административную аутентификацию.

   Исправление: единая политика допуска для обоих способов аутентификации. Если во время несовместимой схемы нужны особые правила восстановления, сделать это явным режимом. Недостающий тест: просроченный пароль без установленного флага в migration API.

4. **P2. Аудит блокировки не использует уже написанный transactional outbox.**

   Место: [auth.go](../internal/server/auth.go), строки 159–165 и 261–267; [user_repo.go](../internal/server/repository/user_repo.go), строки 704–728; [management.go](../internal/server/management.go), строки 635–641.

   Реальная аутентификация вызывает `IncrementFailedLoginAttempts`, коммитит блокировку и затем отдельно вызывает `auditAction`. Ошибка записи аудита только логируется: блокировка может остаться без записи административного журнала. Последующие попытки при `attempts >= 5` повторяют аудит блокировки, хотя нового перехода состояния уже нет.

   `IncrementFailedLoginAttemptsWithOutbox` решает атомарность и запись на пятой попытке, но его production-вызовов не найдено: есть определение, mock и unit-тест. Тест `TestUserRepositoryIncrementFailedLoginAttemptsWithOutboxRollsBackOnEnqueueFailure` проверяет не тот путь, которым пользуется HTTP login.

   Исправление: подключить outbox-вариант к auth-интерфейсу и обоим обработчикам. Тестировать через HTTP-сценарий ошибку enqueue и отсутствие повторных событий блокировки. Смена пароля также пишет аудит отдельно от транзакции изменения: это смежный пробел того же механизма.

5. **P2. Уменьшение лимита загрузки блокирует скачивание старых больших вложений.**

   Место: [attachment_server.go](../internal/server/services/attachment_server.go), строки 417–425; [s3.go](../internal/server/storage/s3.go), метод `DownloadFileToWriter`; [attachments.go](../internal/server/attachments.go), метод `downloadAttachment`.

   `StreamAttachment` использует текущий `max_file_size_mb` как предел чтения существующего объекта. Например, файл 20 МБ, ранее загруженный при лимите 30 МБ, перестанет скачиваться после снижения лимита до 10 МБ. S3-адаптер отвергает объект до записи тела. HTTP-обработчик уже подготовил заголовки вложения и лишь логирует ошибку, поэтому клиент не получает нормальную структурированную причину отказа.

   Исправление: отделить ограничение новых загрузок от безопасного предела скачивания сохранённого объекта; проверять размер по метаданным и абсолютному пределу. Ошибку открытия объекта возвращать до фиксации ответа; обрыв после начала потока обрабатывать отдельно. Недостающий тест: загрузить при большом лимите, уменьшить настройку, скачать прежний файл.

6. **P2. Защита от определения существования логина по времени реализована только для обычного входа.**

   Место: [auth.go](../internal/server/auth.go), строка 258; [management.go](../internal/server/management.go), строка 576.

   В `login` даже для неизвестного пользователя выполняется bcrypt на dummy hash. В обязательной смене пароля и migration Basic Auth условие замыкается на `user == nil`: bcrypt для отсутствующего пользователя не выполняется. Общая задержка 200 мс не устраняет дополнительное время bcrypt для существующего логина. Сравнение серии измерений потенциально позволяет отличать существующие имена; сетевые измерения в рамках ревью не выполнялись.

   Исправление: использовать общий механизм проверки с dummy hash. Текущий `TestLoginVerifiesPasswordOnceForUnknownAndKnownUsers` проверяет только `login`; распространить проверку количества вызовов на другие публичные способы аутентификации.

**Клиент: desktop и frontend**

7. **P2. Регистрация и создание связи не имеют корректного восстановления после частичного успеха.**

   Место: [useDocumentRegistrationActions.ts](../frontend/src/hooks/useDocumentRegistrationActions.ts), строки 81–94; [document_command_idempotency.go](../internal/server/repository/document_command_idempotency.go), проверка `storedHash != requestHash`.

   Сначала `Register` сохраняет документ, затем отдельный `LinkDocuments` создаёт связь. При ошибке второго запроса UI остаётся в состоянии ошибки регистрации; ID уже созданного документа отдельно не сохраняется, ключ идемпотентности не меняется. Если пользователь изменит форму и повторит отправку, сервер отвергнет новый payload с прежним ключом. Закрытие и открытие формы не сбрасывает ключ в этом hook.

   Если связь была записана, но её HTTP-ответ потерян, повтор с прежним payload возвращает прежний документ и снова пытается вставить уже существующую связь; ограничение уникальности пары документов мешает завершить сценарий обычным повтором.

   Исправление: явно различать неопределённый результат регистрации, уже созданный документ и незавершённую связь. Повтор регистрации должен сохранять исходную команду; повтор связывания должен быть идемпотентным. Новый ключ нельзя безусловно выдавать после транспортной ошибки — это создаст риск дубликатов.

   Актуальность тестов: [documentRegistration.test.tsx](../frontend/test/components/documentRegistration.test.tsx), строки 24–43, повторяет запрос с изменённым `content` и прежним ключом; mock безусловно принимает его. Это не проверяет реальный серверный контракт после commit. Нужны сценарии `Register committed → Link failed`, потерянного ответа и повторного открытия формы.

8. **P2. При ошибке второго файла теряется информация об успешной загрузке первого.**

   Место: [attachment_desktop.go](../internal/desktop/services/attachment_desktop.go), методы `Upload` и `UploadForAssignment`, в частности строки 129–135; [useAttachments.tsx](../frontend/src/hooks/useAttachments.tsx), обработчик `uploadFile`.

   Файлы отправляются последовательно. После успешного первого upload ошибка второго приводит к `return nil, err`; первый файл остаётся на сервере. Frontend получает только ошибку и не вызывает `loadFiles`, поэтому список не отражает фактически сохранённый файл. Повтор выбора всего набора загружает первый файл ещё раз.

   Исправление: возвращать структурированный результат по файлам или хотя бы явно сообщать частичный успех и обновлять список после ошибки. Нужен тест из двух файлов: первый успешно сохраняется, второй отклоняется. Имеющиеся тесты ошибок скачивания/одиночных операций не покрывают этот сценарий.

9. **P2. Законный файл нельзя открыть, если Downloads перенесён через символическую ссылку.**

   Место: [attachment_desktop.go](../internal/desktop/services/attachment_desktop.go), строки 263–277.

   Проверка разрешает символические ссылки для самого файла, но для разрешённого корня делает только `filepath.Abs`. Если `~/Downloads` указывает на другой каталог, скачивание работает через ссылку, а последующее `OpenFile`/`OpenFolder` сравнивает канонический путь файла с неканоническим корнем и возвращает запрет.

   Подтверждение: дополнительная проверка создала Downloads как symlink, сохранила внутри файл и воспроизвела отказ валидатора.

   Исправление: канонизировать обе стороны сравнения, сохранив запрет выхода за корень. Отдельно `defaultDownloadDir` жёстко выбирает `$HOME/Downloads`, не учитывая системное перенаправление каталога загрузок; это дополнительное ограничение переносимости. Тестировать ссылку самого корня отдельно от ссылки внутри него на посторонний файл.

10. **P2. Ответ старого поиска перезаписывает результаты нового ввода.**

    Место: [useReferenceSearch.ts](../frontend/src/hooks/useReferenceSearch.ts), строки 21–39 и 51–63.

    Оба hook без проверки актуальности записывают результат каждого завершившегося запроса. Если запрос A медленнее более позднего B, последним отображается A. Очистка поля также не инвалидирует незавершённый запрос: старые варианты снова появляются после очистки.

    Исправление: использовать существующий `LatestRequest` или счётчик версии с инвалидацией при коротком/пустом запросе. Недостающие тесты: ответы B→A, очистка до ответа A, поздняя ошибка A после успешного B. Проверки утилиты `LatestRequest` не защищают hook, который её не использует.

11. **P2. Карточка документа молча ограничивает список поручений первыми 100.**

    Место: [useAssignments.ts](../frontend/src/hooks/useAssignments.ts), запрос с `page: 1`, `pageSize: 100`, `showFinished: true` и возврат только `result.items`.

    Информация об общем количестве/следующих страницах отбрасывается. В `DocumentAssignmentWorkflowPanel` действия выбираются из полученного подмножества. При большом количестве поручений часть действующих поручений может не попасть в карточку; пользователь не видит ни продолжения списка, ни признака усечения. Это особенно заметно при накоплении завершённых поручений, которые запрашиваются вместе с действующими.

    Исправление: пагинация списка и отдельный запрос необходимых действий либо явная загрузка всех страниц с разумным ограничением. Недостающий тест: более 100 поручений с доступным действием за первой страницей.

**Лишний код и состояние тестов**

12. **P3. Есть методы, покрываемые тестами, но не используемые рабочими цепочками.**

    Помимо outbox-метода из замечания 4, поиск ссылок не нашёл production-вызовов [DocumentAccessService.RequireResolvedRead](../internal/server/services/document_access_service.go), строка 533: найдены определение и его тесты. В рабочем коде используется, в частности, `RequireReadResolved`. Аналогично старый `UserRepository.ResetPassword` остаётся в широком `UserStore`, mock и тестах, тогда как HTTP-сброс пароля использует `ResetPasswordWithOutbox`.

    Это кандидаты на удаление после проверки интерфейсов и генерации mock, а не основание удалять экспортируемые методы по одному результату поиска. Тесты таких ветвей повышают покрытие, не подтверждая работу реального маршрута. В проверенной структуре frontend отдельных модулей без входящих импортов не выявлено; вывод о полном отсутствии неиспользуемых экспортов из этого не следует.

13. **P2. Компонентный тест резервного копирования нестабилен по времени.**

    Место: [backupTab.test.tsx](../frontend/test/components/backupTab.test.tsx), тест на строке 88.

    Общий запуск: 47 компонентных тестов прошли, один завершился по таймауту 15 секунд. Точечный повтор того же теста прошёл. Сценарий использует реальные задержки повторного запроса каталога, несколько открытий/закрытий Modal и ожидания до пяти секунд. Поэтому первый сбой нельзя уверенно приписать продуктовой регрессии.

    Исправление: разделить проверки сохранности каталога и диалога, управлять таймерами повтора вместо ожидания реальных секунд. Не маскировать проблему только увеличением общего таймаута. Повтор всего набора не выполнялся: проверен именно упавший тест.

Исходники проверок и логи сохранены в `/tmp/docflow-review-*` текущего окружения.

Интеграционный стек PostgreSQL/SeaweedFS/SMB, восстановление реального backup, race detector, сборки Windows/Wails, интерактивные E2E и сканеры CVE зависимостей не запускались. Поэтому отчёт не подтверждает отсутствие гонок, проблем платформенных API или известных уязвимостей сторонних пакетов; версии зависимостей не объявляются устаревшими без такой проверки. SQL в замечании 1 проверен чтением запроса, без отдельного прогона реальной БД.

Практический порядок исправления: закрыть обход upload и переполнение ограничителя; выровнять аутентификацию и подключить аудит к outbox; затем исправить восстановление клиентских операций и добавить перечисленные тесты на реальные границы между слоями.
