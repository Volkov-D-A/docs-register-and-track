# Код-ревью перехода на `docflow-server`

Дата ревью: 3 сентября 2026 года  
Проверенная ревизия: `d4ec70e`  
Базовая ревизия для сравнения: `b1665de`

## Резюме

Переход на промежуточный сервис в целом проведён последовательно: защищённые данные и операции вынесены в `docflow-server`, клиент обращается к нему через HTTP-клиенты, добавлены сессии, разграничение прав, миграции, TLS и серверные тесты. При этом обнаружены две проблемы высокого приоритета и несколько проблем среднего приоритета, которые желательно устранить до промышленной эксплуатации.

Главные риски:

1. режим обслуживания не блокирует прикладные API во время миграции или отката схемы;
2. первый администратор может быть создан любым сетевым клиентом, успевшим первым вызвать открытый endpoint начальной настройки;
3. desktop-приложение публикует через Wails внутренние серверные методы и сеттеры зависимостей;
4. истёкшая или отозванная сессия не переводит интерфейс в состояние выхода;
5. ответы API раскрывают внутренние тексты ошибок;
6. production Compose ссылается на отсутствующий `Caddyfile`.

Рекомендуемый порядок исправлений: блокировка API в maintenance mode, защита bootstrap-процедуры, сокращение поверхности Wails, единая обработка `401`, безопасный формат ошибок, исправление production Compose.

## Область и методика проверки

Проверено изменение архитектуры от прямого доступа desktop-клиента к данным до работы через `docflow-server`, включая:

- HTTP-маршруты, аутентификацию, сессии и права доступа;
- жизненный цикл сервера, миграции и rollback;
- Go-клиенты сервера и Wails-сервисы;
- загрузку и скачивание вложений;
- TLS с внутренним CA и Docker Compose;
- оставшийся клиентский код и сгенерированные Wails bindings;
- модульные тесты, race detector, статический анализ и frontend-проверки.

## Найденные проблемы

### 1. Высокий приоритет: maintenance mode не блокирует прикладные API

`PrepareRollback` включает режим обслуживания и останавливает worker: [`internal/background/lifecycle.go`](../internal/background/lifecycle.go#L134). Однако прикладные маршруты регистрируются напрямую через `requireSession`/`requirePermission`, а итоговый handler оборачивается только логированием запросов: [`internal/server/management.go`](../internal/server/management.go#L288).

Проверка `lifecycle.CheckReady()` используется для readiness endpoint, но не является общей защитой прикладных маршрутов: [`internal/server/management.go`](../internal/server/management.go#L404).

Последствия:

- во время применения или отката миграции пользователи могут читать и изменять данные на меняющейся схеме;
- возможны частично выполненные операции, ошибки SQL и нарушение согласованности данных;
- после успешного rollback сервис может оставаться в maintenance mode, но бизнес-запросы всё равно продолжат исполняться;
- балансировщик, не успевший убрать instance после изменения readiness, не предотвращает запросы по уже установленным соединениям и прямой доступ к instance.

Рекомендация: добавить общий middleware, который возвращает `503 Service Unavailable` для прикладных API при maintenance/rollback. Явно разрешить только `live`, `ready`, безопасные status endpoints и необходимые административные endpoints миграций. Добавить конкурентный тест, который удерживает миграцию/rollback и проверяет, что запись документа и вложения не достигает service/repository слоя.

### 2. Высокий приоритет: перехват начальной учётной записи администратора

Endpoint `POST /api/v1/auth/setup` доступен без аутентификации: [`internal/server/management.go`](../internal/server/management.go#L294). Обработчик проверяет только отсутствие пользователей и принимает пароль из запроса: [`internal/server/auth.go`](../internal/server/auth.go#L69).

Транзакционная или advisory-блокировка в repository защищает от одновременного создания двух администраторов, но не подтверждает личность инициатора. При доступности сервиса по сети первый клиент может назначить свой пароль раньше легитимного администратора.

Последствия: полный захват новой инсталляции без предварительной учётной записи.

Рекомендация: требовать одноразовый bootstrap-secret из защищённой переменной окружения/файла либо выполнять создание первого администратора локальной CLI-командой. После успешной инициализации секрет должен стать непригодным. Не полагаться только на `CountUsers() == 0`.

### 3. Средний приоритет: Wails публикует внутренние методы серверных сервисов

Один тип `AttachmentService` используется одновременно как desktop-фасад и серверная реализация. В результате bindings экспортируют в renderer методы, которые ему не нужны: `AuthorizeDownload`, `UploadContent`, `StreamAttachment`, `MaxUploadSize`, а также `Set*`-методы зависимостей: [`frontend/wailsjs/go/services/AttachmentService.d.ts`](../frontend/wailsjs/go/services/AttachmentService.d.ts#L11).

Desktop-конструктор заполняет только server client и функцию выбора файлов: [`internal/services/attachment.go`](../internal/services/attachment.go#L58). Например, доступный из bindings `MaxUploadSize()` обращается к неинициализированному `settingsService`: [`internal/services/attachment.go`](../internal/services/attachment.go#L327). Вызов такого метода из renderer способен вызвать panic/DoS. Публичные сеттеры также позволяют менять внутренние зависимости объекта после создания.

Если в renderer появится XSS или будет скомпрометирована frontend-зависимость, избыточная поверхность bindings увеличивает последствия атаки.

Рекомендация: разделить типы на узкий Wails-фасад и внутреннюю серверную реализацию. В bindings должны оставаться только операции, действительно вызываемые UI. Серверные методы, интерфейсные сеттеры и методы с `context.Context`, `io.Reader`/`io.Writer` не должны экспортироваться в renderer. Добавить тест/проверку allowlist публичных Wails-методов.

### 4. Средний приоритет: клиент не завершает сессию после `401 Unauthorized`

Общий HTTP-код клиентских операций декодирует ошибку, но не очищает token при `401`: [`internal/serverclient/users.go`](../internal/serverclient/users.go#L93), [`internal/serverclient/auth.go`](../internal/serverclient/auth.go#L220). Frontend store сбрасывает пользователя в основном при явном logout или смене пароля: [`frontend/src/store/useAuthStore.ts`](../frontend/src/store/useAuthStore.ts#L135).

Сценарии воспроизведения:

- истёк TTL сессии;
- администратор деактивировал пользователя;
- сессия отозвана или удалена;
- пароль сброшен с инвалидированием старых сессий.

UI при этом продолжает считать пользователя авторизованным, а прикладные операции начинают независимо завершаться ошибкой. Восстановление требует ручного logout или перезапуска.

Рекомендация: централизованно обрабатывать `401`: атомарно очищать token, уведомлять auth store, очищать чувствительное пользовательское состояние и переводить приложение на экран входа. Не выполнять автоматический повтор изменяющего запроса без нового входа. Добавить тесты на expiry, revoke, deactivate и password reset.

### 5. Средний приоритет: API раскрывает внутренние ошибки

`writeAPIError` возвращает клиенту необработанный `err.Error()` для любых статусов, включая `5xx`: [`internal/server/management.go`](../internal/server/management.go#L641). Та же функция используется при ошибках repository, проверки сессии и аутентификации: [`internal/server/auth.go`](../internal/server/auth.go#L138), [`internal/server/auth.go`](../internal/server/auth.go#L303). Readiness также возвращает внутренний текст ошибки зависимости: [`internal/server/management.go`](../internal/server/management.go#L404).

Текст ошибки может содержать имена таблиц/полей, детали SQL, адреса инфраструктуры, пути или сведения о конфигурации. Это облегчает разведку и создаёт нестабильный внешний контракт.

Рекомендация: для `5xx` возвращать стабильные `code`, безопасное общее сообщение и `requestId`; полную причину записывать только в server log. Пользовательский текст разрешать только для явно классифицированных `AppError` с безопасным сообщением. Для readiness наружу отдавать только состояние компонента, без исходной ошибки.

### 6. Средний приоритет: production Compose использует неверный путь к Caddyfile

В [`docker-compose.prod.example.yaml`](../docker-compose.prod.example.yaml#L75) указан bind mount:

```yaml
- ./caddy/Caddyfile:/etc/caddy/Caddyfile:ro
```

Каталога `caddy` в корне репозитория нет. Фактический файл находится в `build/caddy/Caddyfile`, и основной [`docker-compose.yaml`](../docker-compose.yaml#L95) использует именно этот путь. Инструкция по внутреннему CA также оперирует `build/caddy`: [`docs/https-internal-ca-setup.md`](https-internal-ca-setup.md#L83).

`docker compose config` не выявляет отсутствие bind-source и успешно формирует конфигурацию, но запуск Caddy с таким mount завершится ошибкой или создаст каталог вместо ожидаемого файла — в зависимости от окружения Docker.

Рекомендация: заменить источник на `./build/caddy/Caddyfile` либо монтировать `./build/caddy:/etc/caddy:ro`. Добавить smoke test, запускающий production-профиль и проверяющий HTTPS endpoint.

### 7. Низкий приоритет: timing side channel при проверке логина

Проверка credentials использует short-circuit:

```go
if user == nil || !security.VerifyPassword(user.PasswordHash, req.Password) {
```

См. [`internal/server/auth.go`](../internal/server/auth.go#L138). Для неизвестного пользователя bcrypt не выполняется, а для существующего выполняется; фиксированная задержка в 200 мс добавляется в обоих ошибочных сценариях и не устраняет разницу времени bcrypt полностью. Серия измерений может помочь определить существующие логины.

Рекомендация: при отсутствии пользователя сравнивать пароль с заранее рассчитанным dummy bcrypt hash, сохраняя одинаковый основной путь вычислений. Rate limit оставить дополнительным уровнем защиты. Добавить статистический/структурный тест, который подтверждает выполнение password verification для обоих случаев, не делая тест зависимым от жёсткого порога времени.

## Избыточный и оставшийся клиентский код

### Совмещение desktop- и server-ролей в сервисах

`AuthService` сохраняет прямой repository/database fallback, хотя production desktop создаётся с server client, а сервер использует собственные обработчики. Этот путь преимущественно поддерживается старыми тестами и усложняет понимание доверенной границы: [`internal/services/auth_service.go`](../internal/services/auth_service.go).

`AttachmentService` содержит desktop-операции выбора/открытия файлов и серверные операции object storage в одном публичном типе. Это является причиной избыточных bindings и многочисленных веток `if s.server != nil`.

Рекомендация: после подтверждения отсутствия legacy-сценария выделить отдельные типы, например `DesktopAttachmentFacade` и `ServerAttachmentService`; для аутентификации оставить в desktop только адаптер `serverclient.AuthClient`. Старую реализацию удалять отдельным изменением после миграционных тестов.

### Неиспользуемые зависимости `UserService`

Поля `userRepo` и `auth` всё ещё находятся в `UserService`: [`internal/services/user_service.go`](../internal/services/user_service.go#L15), тогда как актуальные операции используют `server`/`executors`. Конструктор с repository поддерживает старую форму объекта, но повышает риск случайного возврата прямого доступа к данным.

Рекомендация: удалить поля и legacy-конструктор после проверки всех production composition roots и тестов; оставить обязательные server interfaces в конструкторе, чтобы некорректное состояние нельзя было создать.

### Закомментированные старые тесты вложений

В [`internal/services/attachment_test.go`](../internal/services/attachment_test.go#L194) остался крупный закомментированный блок тестов старого base64-пути загрузки. Он не исполняется и создаёт ложное впечатление покрытия.

Рекомендация: удалить блок. Если содержащиеся в нём сценарии по-прежнему важны, восстановить их как тесты streaming HTTP API, а не хранить закомментированный код.

## Недостающее тестовое покрытие

Обязательные тесты перед production rollout:

1. При maintenance/apply/rollback все бизнес-операции возвращают `503`, а разрешённые health/migration endpoints продолжают работать.
2. Bootstrap admin требует секрет или локальный доверенный канал; конкурентные запросы не позволяют перехватить установку.
3. Истечение, отзыв, деактивация и reset password очищают desktop-сессию и возвращают UI на login.
4. Wails bindings соответствуют allowlist и не содержат внутренних `Set*`, streaming и repository-oriented методов.
5. TLS handshake отклоняет сертификат от другого CA и сертификат с неверным DNS-именем. Эти сценарии прямо перечислены в [`docs/https-internal-ca-setup.md`](https-internal-ca-setup.md#L349), но текущие тесты проверяют главным образом загрузку PEM/root pool.
6. Production Compose действительно поднимает Caddy и проходит HTTPS health check.
7. Есть нагрузочные/конкурентные тесты rate limiter, telemetry ingest и streaming больших вложений.
8. Ошибки `5xx` не содержат SQL, DSN, filesystem paths и внутренних сообщений зависимостей.

## Результаты выполненных проверок

Успешно:

- `go test ./internal/server ./internal/serverclient ./internal/services ./internal/app`;
- `go test -race ./internal/serverclient ./internal/server`;
- `go vet ./internal/server ./internal/serverclient ./internal/services ./internal/app`;
- frontend lint;
- frontend production build;
- синтаксическая сборка обоих Compose-файлов через `docker compose config`.

Замечания:

- для Go-тестов использовался отдельный `GOCACHE` в `/tmp`, потому что первый запуск со стандартным cache завершился инфраструктурной ошибкой `testing/internal/testdeps: package testmain cannot find package`;
- полный `npm test` нестабилен на стандартном timeout 5 секунд: падали `assignmentSeriesModal.test.tsx` и `outgoingPageDirtyFlow.test.tsx`; отдельный запуск `assignmentSeriesModal` с timeout 15 секунд прошёл. Это похоже на нестабильность/слишком жёсткие таймауты, но требует отдельной диагностики;
- PostgreSQL integration suite и реальный Docker/HTTPS smoke test не запускались;
- `docker compose config` подтвердил, что production bind-source разрешается в отсутствующий корневой `caddy/Caddyfile`, но сам контейнер не запускался.

## План устранения

### До развёртывания

1. Закрыть business API middleware-ом maintenance mode и покрыть конкурентными тестами.
2. Защитить создание первого администратора bootstrap-secret или локальной CLI-процедурой.
3. Исправить путь к Caddyfile и выполнить HTTPS smoke test production Compose.
4. Перестать возвращать внутренние тексты ошибок в `5xx`.

### Следующим изменением клиента

1. Ввести единый обработчик потери сессии по `401`.
2. Разделить Wails-фасады и серверные реализации, сократить bindings до allowlist.
3. Удалить repository fallback и неиспользуемые поля после проверки composition roots.
4. Удалить закомментированные legacy-тесты и заменить актуальными streaming-тестами.

### Усиление качества

1. Добавить негативные TLS handshake tests.
2. Стабилизировать frontend-тесты и их ожидания асинхронных операций.
3. Добавить integration/smoke проверки production-конфигурации в CI.
4. Проверить устойчивость login rate limiting, telemetry и больших загрузок под конкуренцией.
