# Поэтапный аудит кодовой базы Docflow

Дата: 2026-10-26. Исполнение и границы проверенного охвата зафиксированы в
[результатах аудита](codebase-audit-results.md).

## Принятое условие исполнения

Пользователь подтвердил отсутствие рабочей БД и необходимость только текущего
контракта: обратная совместимость не требуется. Пункты о сохранённых данных
ниже применяются как предмет проверки, а не основание сохранять старые пути.
Проверки безопасности текущего формата, доступа и состояния схемы остаются.

## Цель и границы

Выявить и устранить код и данные без актуального назначения: недостижимые реализации, остатки прежней архитектуры, ненужную совместимость, лишние вычисления и запросы, устаревшие тестовые ожидания, моки, зависимости и инфраструктуру. Отдельно найти повторяющуюся логику и определить обоснованные места переиспользования.

Аудит охватывает исходники Go и TypeScript, HTTP/Wails-контракты, PostgreSQL, фоновые процессы, события, резервирование, конфигурацию, сборку, тесты и документацию. Сгенерированные файлы исследуются через источник генерации. Локальные артефакты учитываются отдельно от отслеживаемых исходников.

Сокращение числа строк не является самостоятельной целью. Результат должен уменьшать число реализаций, преобразований, запросов и поддерживаемых контрактов, сохраняя актуальные сценарии, права доступа и необходимые эксплуатационные гарантии.

## Правила доказательства и ведения аудита

1. Отсутствие текстовых ссылок, нулевое покрытие или слово `legacy` — повод проверить, но не основание удалить. Учитывать интерфейсы Go, runtime-регистрации Wails, маршруты HTTP, сериализацию, динамические ключи React, build tags, embed, генераторы и внешних потребителей.
2. Разделять использование в production, только в тестах, только в tooling и потенциальное внешнее использование. Тест, вызывающий метод, сам по себе не доказывает актуальность метода. Редкий recovery-сценарий остаётся production-сценарием.
3. Для каждого кандидата прослеживать цепочку от точки входа до данных и побочных эффектов и обратно: кто создаёт, передаёт, читает, сохраняет и удаляет результат.
4. Отдельно установить поддерживаемые версии клиента, сервера, схемы, backup-формата и сохранённых событий. Проверка совместимости текущих компонентов и отказ от опасного старого формата могут быть необходимой защитой, а не поддержкой прежнего поведения.
5. Если удаление затрагивает сохранённые данные или внешний контракт, сначала зафиксировать решение об их судьбе. При недостатке доказательств сохранять код с конкретной причиной и условием повторного рассмотрения.
6. Удалять подтверждённый хвост целиком: реализация, интерфейс, адаптер, DTO, SQL, настройки, события, моки, фикстуры, ожидания, документация. Затем повторно искать ставшие ненужными зависимости.
7. Выполнять изменения небольшими завершёнными цепочками. Не объединять массовое удаление, изменение бизнес-правил и создание общей абстракции в одну трудно проверяемую правку.

Каждая находка получает запись:

| Поле | Содержание |
| --- | --- |
| ID и категория | Недостижимый код / совместимость / лишние данные / дубль / тесты / инфраструктура |
| Место | Файлы, символы, маршрут, поле DTO, таблица или настройка |
| Текущее назначение | Какой актуальный сценарий должен обслуживать элемент |
| Производители и потребители | Включая тесты, фоновые задачи, генерацию и внешние вызовы |
| Доказательства | Ссылки на код, поиск, граф вызовов, тест или наблюдение |
| Решение | Удалить / упростить / переиспользовать / сохранить / исследовать |
| Риск и зависимости | Контракты, сохранённые данные, доступ, платформы, связанные находки |
| Проверка | Конкретный сценарий и минимальный достаточный способ проверки |
| Завершение | Изменение, результат проверки либо причина отсрочки и условие пересмотра |

Статусы находок: кандидат → исследован → решение принято → исправлен → проверен. Для сохранённых и отложенных находок фиксировать причину; не считать их удалёнными или исправленными.

## Этап 0. Зафиксировать исходное состояние и правила совместимости

**Действия**

- Записать commit, состояние рабочего дерева, платформы и доступные инструменты. Отделить существующие пользовательские изменения от результатов аудита.
- Сверить README, техническую документацию, Go/npm manifests, Makefile и реальные точки запуска. Документацию использовать как ориентир, факты проверять по коду.
- Составить таблицу поддерживаемых комбинаций desktop/server, схемы БД, backup-форматов, конфигураций и форматов событий. Учесть смешанные версии во время обновления, восстановление и накопленные очереди.
- Отметить ограничения среды: недоступная Windows, Docker, SMB или другие проверки. Не выдавать отсутствие проверки за подтверждение корректности.
- Записать известные исходные сбои только по уже доступным сведениям; запускать воспроизведение при необходимости, без полного предварительного прогона всех тестов.

**Результат:** зафиксированная база сравнения и критерии, когда совместимость можно снять. Нерешённые вопросы блокируют только зависящие от них удаления.

## Этап 1. Построить карту исполняемой системы и реестр покрытия аудита

**Области:** `main.go`, `cmd/docflow-server`, `internal/desktop/app`, `internal/server`, `frontend/src/App.tsx`, `frontend/src/components/AppRouter.tsx`, `tools`, `scripts`, `testing`, `build`.

- Перечислить точки входа: desktop startup/shutdown, CLI-команды, HTTP-маршруты, Wails Bind, страницы, фоновые worker, подписки, генераторы и служебные команды.
- Построить карту зависимостей: frontend → Wails services → serverclient → HTTP handlers → services/ports → repository → PostgreSQL/effects/outbox → получатели событий.
- Проверить границы desktop/server/shared, включая транзитивные импорты и тестовую композицию. Общие пакеты не должны втягивать сервер, desktop или Wails.
- Создать реестр каталогов и доменных цепочек со статусами «не проверено / проверено / есть открытые находки». Исключения и сгенерированные области указывать явно.
- Разделить tracked-файлы, генерируемые bindings/assets, build output, кэши и локальные отчёты. Наличие `.test-build`, `dist` или бинарника на диске не доказывает наличие лишнего исходника в Git.

**Результат:** карта точек входа, зависимостей и охвата. Дальнейшие этапы должны пройти все строки реестра, а не только крупные или недавно изменённые файлы.

## Этап 2. Найти недостижимый код и остатки реорганизации

**Области:** все Go-пакеты, `frontend/src`, registries, factories, composition roots, generated API.

- Найти функции, методы, типы, константы, поля, React-компоненты, hooks, stores и exports без актуальных потребителей.
- Для экспортируемых Go-методов проверить интерфейсы, Wails и runtime-регистрации. Для frontend — lazy imports, конфиги видов документов, динамический выбор страниц и событий.
- Выделить методы, вызываемые только тестами, и тестовые constructors/setters, расширяющие production API без необходимости.
- Проверить старые сервисы, репозитории, локальную авторизацию и пути к БД/хранилищу, которые могли пережить перенос операций на сервер.
- Найти пустые адаптеры, forwarding-методы и одноразовые обёртки. Сохранять обёртку, если она обеспечивает границу, преобразование ошибок, контекст, авторизацию или жизненный цикл.
- Проверить неиспользуемые ветви конфигураций, флаги, TODO, закомментированные реализации, no-op callbacks, отключённые страницы и недостижимые fallback.
- Применять доступные статические анализаторы как генератор кандидатов. Для Go учитывать платформенные файлы и build tags; для TypeScript — код вне основного tsconfig и генерируемые bindings.

**Результат:** доказанные кандидаты на удаление с указанием всех зависимых элементов. Поиск повторяется после каждого удаления до исчезновения вызванных им хвостов.

## Этап 3. Пересмотреть совместимость и параллельные контракты

**Области:** HTTP API, `internal/models`, `internal/dto`, serverclient, Wails, конфигурации, migrations, backup, outbox.

- Найти aliases, старые имена/коды, альтернативные JSON-поля, необязательные параметры с историческим fallback, несколько схем ошибок и дублирующие endpoints.
- Для каждой ветви совместимости записать: какой старый производитель ещё существует, какие данные могли сохраниться, когда прекращена запись старого формата и что произойдёт при удалении чтения.
- Проследить оба режима пагинации: cursor и page/totalCount. Выяснить реальные потребности внутренних вызовов, отчётов и UI; удалять режим только после переноса последнего потребителя.
- Проверить преобразования document-kind codes и отображаемых названий; отделить ключи UI-страниц от системных кодов документов.
- Проверить поддержку прежних форматов outbox payload, событий, результатов операций, backup manifest, env/config и persisted UI state.
- Отделить декодирование старого формата от запрета его применения. Негативные тесты, подтверждающие отказ от старых полей или backup, не считать устаревшими автоматически.
- Сопоставить договорённость о версиях с фактическими проверками версии и build identity; устранить лишь доказанно избыточные ветви.

**Результат:** таблица совместимости с решением для каждой ветви: необходима, удаляется либо ожидает решения по данным/потребителям. Для удаления указаны порядок обновления и переход сохранённых данных.

## Этап 4. Провести сквозной аудит данных и лишней работы

Для каждого существенного результата составить путь:

`источник → SQL/вычисление → модель → DTO → JSON → serverclient → Wails → React → фактическое использование`.

- Составить матрицу полей для list/card/search/statistics/report/bootstrap/access-summary: где поле создаётся, передаётся, читается, сохраняется, экспортируется или используется для решения.
- Найти SQL-колонки, JOIN, COUNT, агрегаты, ассоциации и дополнительные запросы, результаты которых отбрасываются в mapper или следующем слое.
- Проверить загрузку полной карточки ради списка или нескольких полей; повторную загрузку связанных пользователей, подразделений, прав и справочников; дубли list/card projections.
- Найти поля HTTP/Wails-ответов, которые доходят до frontend, но не читаются; React-state, selectors и derived values, которые записываются без использования.
- Проверить запросы, запущенные без использования результата: отличать лишнее чтение от команды с побочным эффектом, прогрева, audit и авторизационной проверки.
- Исследовать результаты async-запросов, отмену и обработку устаревших ответов: защитная отмена не означает, что запрос всегда лишний.
- Найти повторные запросы из effects, подписок, polling и инвалидаций; проверить, не загружаются ли данные неактивных вкладок и недоступных разделов.
- Проверить создание экспортов, временных файлов, журналов и метрик без потребителя или очистки; учесть скачивание и диагностику вне UI.
- Для производительных запросов фиксировать измеряемое изменение: число запросов, объём ответа, allocations или план SQL. Сравнивать на одинаковом сценарии без произвольных порогов времени.

**Результат:** перечень полей и операций без потребителя и исправления по всей цепочке. Удаление поля из UI должно сопровождаться проверкой возможности убрать его получение и передачу.

## Этап 5. Проверить PostgreSQL и жизненный цикл сохранённых данных

**Области:** `internal/server/database`, `repository`, `models`, `ports`, SQL-фикстуры и backup/restore.

- Построить CRUD-карту таблиц и колонок: кто пишет, читает, чистит, экспортирует и восстанавливает; учесть ограничения, триггеры, функции, индексы и каскады.
- Найти write-only поля, заброшенные таблицы, историю без читателей, дублируемые значения, неиспользуемые связи и индексы. Нулевое использование индекса на тестовой БД не доказывает ненужность.
- Проверить SQL, который заполняет старые поля, хотя приложение их уже не читает; убрать запись вместе с контрактом и схемой по принятому решению.
- Проверить свежую установку и обновление каждой поддерживаемой схемы отдельно. В репозитории сейчас базовая пара `001_docflow.up.sql` / `001_docflow.down.sql`; сначала выяснить, какая схема реально развёрнута и как договорено её обновлять.
- Не переписывать применённую миграцию и не добавлять формальную миграцию без выяснения модели поставки. Для сохранённых БД определить поддерживаемый переход, ограничения восстановления и допустимость потери данных.
- Проверить транзакции, idempotency, outbox inserts, блокировки и гонки: кажущийся лишним SELECT может обеспечивать права, сериализацию или защиту от повторной операции.
- Разделять рабочие данные, аудит, техническую историю и временные записи; отсутствие экрана для данных не означает отсутствие требования к их хранению.

**Результат:** согласованная схема без неподтверждённых удалений, переход данных и целевые PostgreSQL-проверки для изменённого поведения.

## Этап 6. Проверить фоновые задачи, события и эксплуатационные пути

**Области:** `background`, `effects`, `outbox`, `liveevents`, desktop operations/logging, frontend events, backup/SMB.

- Для каждого события сопоставить producer, запись outbox, dispatcher, audience, SSE, desktop adapter, frontend subscriber и refresh. Найти события без подписчиков и подписчиков без producer.
- Проверить устаревшие event names, поля payload, маршрутизацию аудитории, дубли инвалидаций и параллельный polling. Сохранить обоснованный механизм восстановления после пропуска событий.
- Проверить повторные попытки, backlog, terminal states, дедупликацию и очистку. Отсутствие активных сообщений не доказывает, что обработчик не нужен.
- Найти worker, таймеры, goroutines, channels и subscriptions без актуальной задачи, остановки или владельца. Проверить login/logout/reconnect, startup/shutdown и изменение настроек.
- Проверить backup/restore: текущий database-only формат, каталог несовместимых архивов, progress, staging, SMB и cleanup. Отдельно исследовать остатки прежнего объектного хранилища в коде, скриптах, томах, env, документации и тестах.
- Проверить административные, recovery и диагностические маршруты, включая состояние до миграций. Редкие аварийные пути требуют отдельного решения, а не удаления по частоте вызова.

**Результат:** карта событий и фоновых процессов, удалённые бесхозные producer/consumer и подтверждённая работоспособность актуального жизненного цикла.

## Этап 7. Найти дублирование и определить места переиспользования

Проводить после первичного удаления лишних путей, чтобы не объединять устаревшие реализации.

| Область сравнения | Что искать | Возможное место общей логики |
| --- | --- | --- |
| Четыре вида документов | Повтор регистрации, списков, фильтров, карточек, mapping | Существующие document-kind modules, общий shell/hooks; серверные helpers внутри домена |
| HTTP-клиент | JSON, ошибки, headers, ограничения ответа, отмена | `internal/desktop/serverclient`, с сохранением различий auth и streaming |
| Серверные handlers/services | Parsing, pagination, validation, повторяющиеся правила | Узкие helpers слоя; бизнес-правила в серверных сервисах |
| SQL и projections | Повтор фильтров, доступа, scan/mapping | `repository` и узкие проекции; без универсального query-builder ради самого объединения |
| Права и пользователь | Повтор access checks, principal, ФИО | Серверная авторизация; независимые функции представления, где семантика совпадает |
| Frontend | Loading/error/dirty state, forms, refresh, таблицы | Существующие hooks/components/features |
| Даты и строки | Организационная дата, форматирование, имена файлов | Независимые shared/helpers только при одинаковых правилах |
| Тесты | Fixtures, HTTP setup, database setup, builders | Существующие testutil и локальные builders с явными отличиями сценариев |
| Скрипты | Compose lifecycle, readiness, cleanup, release metadata | Узкие helpers scripts/tools/Makefile |

- Разделять текстовое сходство и одну бизнес-концепцию. Составить таблицу совпадений и существенных различий до выделения abstraction.
- Сначала рассмотреть уже существующий общий модуль; найти дубли, появившиеся в обход него, и неиспользуемые режимы самого модуля.
- Сравнить стоимость: сколько реализаций исчезает и сколько параметров, флагов, связей и условий появляется. Если общий helper сложнее отдельных реализаций, сохранить явное различие.
- Не переносить серверную авторизацию в frontend/shared ради устранения похожего кода. Не объединять SQL с разной семантикой прав и не возвращать desktop-зависимость от server.
- Не объединять тестовые ожидания так, чтобы ожидаемое значение вычислялось той же реализацией, которую проверяет тест.
- Для каждого предложения указать старые места, владельца общей логики, сохраняемые различия, последовательность переноса и проверяемые инварианты.

**Результат:** отдельный список решений «переиспользовать / оставить раздельно» с обоснованием; после переноса старые реализации и их adapters удалены.

## Этап 8. Проверить тесты, моки и фикстуры на актуальность

**Области:** Go `*_test.go`, `internal/server/mocks`, `testutil`, Wails contract fixture, `frontend/test`, `testing`, тесты tools/scripts.

- Для каждого набора тестов назвать актуальное правило или риск, который он защищает. Найти проверки удалённых операций, старой структуры данных и снятых требований.
- Отделить устаревшие позитивные ожидания от актуальных негативных тестов: отказ от старого payload, небезопасной конфигурации и несовместимого backup остаётся полезной проверкой.
- Сопоставить моки портов с реальными consumers. Удалить методы и поля, оставшиеся только ради старого интерфейса, fake-сервисы без сценариев, лишние настройки и разросшиеся универсальные fixtures.
- Проверить, не продолжают ли тесты обходить HTTP/server-side principal через старую локальную композицию и не подтверждают ли архитектуру, которой больше нет.
- Найти fixtures со старыми колонками, статусами, именами, схемой и версиями. Проверить, что тесты воспроизводят актуальные defaults, ограничения и маршруты.
- Найти тесты, которые проходят без целевого действия: нет assertions/await, слишком permissive mock, глобальная заглушка, swallowed error, условный ранний выход или skip из-за недоступной БД.
- Для сомнительного теста локально внести контролируемую поломку поведения и проверить, что он падает; вернуть временную правку. Делать выборочно, не разворачивать отдельную массовую кампанию.
- Проверить SQL mocks: не закрепляют ли они число и порядок старых запросов вместо результата. При изменении SQL проверять реальную БД там, где mock не подтверждает нужную семантику.
- Найти дубли сценариев между unit/HTTP/integration/component: сохранять разные границы риска, убирать буквальные повторы без дополнительного доказательства.
- Проверить setup/teardown, изоляцию глобального состояния, таймеры, test-only env, Compose и артефакты. Обновить Wails contract fixture по актуальному контракту, bindings — только штатной генерацией.

**Результат:** тесты подтверждают актуальные правила, моки соответствуют оставшимся портам, фикстуры не удерживают удалённый код. Перед удалением теста указан исчезнувший риск либо оставшаяся проверка того же риска.

## Этап 9. Проверить зависимости, сборку, конфигурации и документацию

- Сопоставить прямые Go/npm dependencies с production, тестами и tooling; учесть CSS, types, side-effect imports, генераторы, embed и платформенные реализации.
- Удалять только подтверждённо ненужные зависимости. Для Go после изменения выполнить `go mod tidy` и просмотреть manifests; npm lockfile обновлять штатным npm. Обновление версий не смешивать с чисткой.
- Проверить Makefile, `build/make`, Dockerfiles, Compose, Wails/Vite/TS/ESLint/Vitest configs и scripts: неиспользуемые targets, env aliases, mounts, ports, stages, assets и устаревшие fallback.
- Проверить полезность tooling и тестов tooling, фактическое включение файлов в линтеры, typecheck, тестовые команды и release gate. Исключённые области внести в реестр покрытия.
- Найти docs и примеры, описывающие удалённые пути, старую схему, команды, объектное хранилище и методы API. Исторические release notes не переписывать как текущую инструкцию; пометить исторический контекст при необходимости.
- Проверить `.gitignore`, `.dockerignore`, содержимое сборочного контекста и упаковки, generated files и stale output. Убирать исходную причину появления артефактов, а не только файлы на диске.

**Результат:** поддерживаемый путь разработки и поставки без забытых зависимостей и конфигураций, документация соответствует итоговому коду.

## Этап 10. Выполнить чистку завершёнными доменными цепочками

Предыдущие этапы задают направления исследования; исправления можно выполнять после доказательства находки, не откладывая все удаления до конца. Для каждого домена последовательно применяются проверки этапов 2–9.

Рекомендуемый порядок обхода:

1. Bootstrap, совместимость, конфигурация, миграции и диагностика.
2. Аутентификация, сессии, пользователи, права и справочники.
3. Входящие, исходящие, обращения и приказы: регистрация, изменение, списки, поиск, карточки, ознакомление.
4. Контроли сроков, соисполнители, регулярные серии и календарные правила.
5. Связи/граф, журналы, аудит, outbox, SSE и обновление UI.
6. Рабочий стол, статистика, отчёты и XLSX/PDF.
7. Backup/restore, SMB, maintenance, logging и shutdown.
8. Оставшиеся shared-пакеты, tooling, сборка и документация.

Для каждой порции:

1. Зафиксировать текущий сценарий, доказательства и целевое состояние.
2. Выбрать и при необходимости дополнить проверку конкретного риска.
3. Удалить или перенести всю связанную цепочку, включая моки и данные.
4. Повторить поиск старых символов, ключей, endpoints, настроек и новых сирот.
5. Выполнить достаточную проверку; просмотреть diff и generated changes.
6. Закрыть находки в реестре, записать ограничения и оставшиеся зависимости.

Приоритет: нарушения границ/прав и лишние побочные эффекты → доказанно неиспользуемые цепочки → лишние данные и запросы → согласованное снятие совместимости → переиспользование и остальные упрощения. Рискованные изменения схемы и восстановления выделять отдельно.

## Этап 11. Проверить результат и закрыть аудит

### Проверки по изменённому риску

| Изменение | Достаточная проверка |
| --- | --- |
| Документация, комментарии, локальные артефакты | Просмотр diff; для ссылок `make docs-links-check` |
| Go-метод или сервис | Целевой тест или затронутый пакет; проверить consumers и интерфейсы |
| React-hook/component | Целевой utility/component test; lint/typecheck по затронутому риску |
| HTTP/DTO/Wails | Проверка формы запроса/ответа и потребителя; штатная генерация при изменении Wails API |
| SQL, схема, транзакции, idempotency | Целевые проверки на изолированной PostgreSQL; полный `make integration-test`, если узких недостаточно |
| События, сессии, lifecycle | Проверка доставки, reconnect/logout/shutdown; race только для затронутой конкурентности |
| Backup, SMB, restore | Соответствующий интеграционный сценарий актуального формата и восстановления |
| Платформенный код и упаковка | Проверка затронутой Linux/Windows сборки; недоступную платформу указать явно |
| Подготовка итогового релиза | `make release-gate` и проверки окружения по README |

Не запускать весь набор после каждой правки. Общую сборку или интеграционный прогон использовать для конкретного оставшегося риска; до тяжёлого запуска объяснять его цель. Недоступность или пропуск интеграционного теста не считать успешной проверкой.

### Критерии завершения

- Все области и доменные цепочки из реестра охвата проверены; исключения названы.
- Каждая находка имеет решение, доказательство и результат проверки либо конкретную причину сохранения/отсрочки.
- Нет подтверждённых хвостов удалённых методов в интерфейсах, DTO, SQL, events, bindings, mocks, fixtures, manifests и документации.
- Для данных без потребителя устранены и передача, и получение, если получение не выполняет отдельной необходимой функции.
- Для совместимости установлен актуальный потребитель/сохранённый формат либо выполнено согласованное снятие поддержки.
- Устранённые дубли имеют одного владельца; оставленные различия объяснены, новая абстракция не нарушает границы архитектуры.
- Тесты защищают текущие сценарии и отказ от запрещённого поведения; удаление тестов не скрывает непроверенный риск.
- Проверены затронутые сценарии, ограничения платформ и окружения отражены в итоговом отчёте.

Итоговый отчёт содержит: охват по этапам и доменам, закрытые находки, оставленные решения, удалённые контракты/зависимости, сокращение лишних запросов/данных, изменения схемы и результаты проверок. Число удалённых строк можно привести справочно; оно не доказывает полноту аудита. Абсолютное отсутствие мёртвого кода нельзя гарантировать одной статической проверкой: вывод должен ограничиваться проверенными конфигурациями, контрактами и сценариями.

## Первые точки исследования по предварительному обзору

Это направления проверки, а не подтверждённые дефекты:

- В технической документации описаны cursor pagination и сохранённый page/totalCount-контракт: установить всех оставшихся потребителей каждого режима.
- В `internal/server/app.go` есть обработка audit payload без audience: проверить формат накопленного outbox и актуальность producer старого payload.
- В `internal/server/backup/progress.go` отмечена совместимость terminal stage с ранее сохранёнными результатами: определить хранение, чтение и срок жизни таких результатов.
- В `internal/server/backup` явно отвергаются старые архивы, а каталог показывает их несовместимыми: это может быть необходимой защитой и не означает поддержку восстановления старого формата.
- В дереве присутствует `scripts/seaweedfs-entrypoint.sh`: проверить тип объекта, tracked-состав, содержимое и реальные ссылки; одно имя не доказывает оставшийся рабочий путь к объектному хранилищу.
- В рабочем дереве удалены прежний план аудита и документы по контролям сроков; техническая документация ссылается на один из удалённых документов. Зафиксировать состояние до проверки ссылок, не восстанавливать пользовательские удаления автоматически.

## Как предотвращать повторное накопление

После завершения аудита сохранить короткий реестр обоснованной совместимости с условием удаления. При дальнейших изменениях проверять затронутую цепочку целиком, удалять старый путь при переносе последнего потребителя и добавлять узкую защиту только для выявленного риска: архитектурной границы, контракта, отсутствия старого поля или поведения. Не вводить обязательный тяжёлый аудит при каждой небольшой правке.
