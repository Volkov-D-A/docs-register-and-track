# План раздела «Отчёты»

## Цель и границы

Добавить самостоятельный раздел «Отчёты» рядом со «Статистикой». Статистика остаётся оперативным обзором; отчёт строится по выбранному периоду и фильтрам, показывает таблицу с итогами и может быть сохранён в Excel или PDF. Регулярные отчёты используют те же определения показателей и фильтров, что и разовый запуск.

Реализованы отдельное право, четыре шаблона, экспорт и серверные расписания с историей. Старые таблицы отчётов во вкладках статистики сохранены: их показатели и фильтры пока отличаются от новых шаблонов, поэтому функциональный паритет для удаления старого пути не достигнут.

Ввести одно системное право `reports` на открытие раздела, получение вариантов фильтров, построение, экспорт, просмотр сохранённых запусков и управление собственными расписаниями. Права `stats_documents`, `stats_assignments`, `stats_system` не дают доступ к отчётам, а `reports` не открывает вкладки статистики. Все операции проверяют право на сервере; скрытие пункта меню лишь отражает решение сервера.

Первый набор шаблонов:

1. Входящие и исходящие письма по организациям.
2. Нагрузка подразделений по периодам.
3. Среднее время исполнения поручений.
4. Доля поручений с нарушением срока.

Конструктор ограничен этими шаблонами и разрешёнными для каждого шаблона измерениями и фильтрами. Произвольные SQL, формулы и колонки пользователь не задаёт.

## Принятые определения

| Показатель | Предлагаемое определение | Проверка на данных |
| --- | --- | --- |
| Период документов | Включительно по `documents.registration_date`; при регулярном запуске — завершённый календарный период в часовом поясе расписания. | Границы месяца, года и смена часового пояса. |
| Организация | Для исходящих — `outgoing_document_details.recipient_org_id`; для входящих — уникальные пары документа и `document_correspondent_registrations.correspondent_org_id`. | У входящего возможны несколько организаций: его учитывают по разу у каждой, а общий итог уникальных документов показывают отдельно от суммы строк. Обращения граждан не имеют этого реквизита. |
| Нагрузка подразделения | Количество созданных поручений типа `execution` основным исполнителям, сгруппированное по календарным месяцам. Подразделение берётся из текущей карточки исполнителя. | Перевод пользователя в другое подразделение меняет ретроспективную группировку. Для исторически неизменяемого распределения потребуется снимок подразделения на дату назначения. |
| Среднее время исполнения | Для поручений типа `execution` с `completed_at` в периоде: среднее от `created_at` до текущего завершения исполнителем (`completed_at`), в календарных сутках с одним десятичным знаком. | `finished` сохраняет `completed_at`; возврат к исполнителю его сбрасывает, поэтому после повторного исполнения учитывается последняя сдача. Рабочие дни и срок от последнего возврата не рассчитываются. |
| Доля просрочки | Числитель — поручения из выбранной когорты с `deadline`, исполненные после срока; знаменатель — все завершённые в периоде поручения с `deadline`. Отдельно показывается открытая просрочка на дату формирования. | Нынешняя статистика применяет другие даты для режимов «всего» и «просрочено». Для исторического среза открытой просрочки нужен снимок или история состояний. |

В каждом отчёте указывать период, дату и часовой пояс формирования, применённые фильтры, формулу/единицу измерения, число исходных записей и версию определения показателя. Пустой знаменатель показывать как «нет данных», а не как 0 %.

## Этапы

### 1. Контракт и право доступа

- Зафиксировать решения по таблице выше и матрицу допустимых фильтров для четырёх шаблонов: период, шаг динамики, вид документа, организация, подразделение, основной исполнитель, номенклатура, статус/наличие срока там, где они применимы.
- Создать миграцию, расширяющую CHECK для `user_system_permissions.permission` значением `reports`; уже выданные права статистики не преобразовывать автоматически. Обновить константу модели, административную форму прав, `CurrentAccessSummary.Sections`, sidebar, маршрутизацию и страницу без доступа.
- Вынести версии контрактов отчётов в DTO: идентификатор шаблона, параметры, колонки с типами, строки, итоги, метаданные определения. Для каждого запроса валидировать период, IDs, допустимые фильтры и лимиты объёма/периода; не принимать SQL-фрагменты от клиента.
- Приёмка: пользователь только с `reports` видит «Отчёты» и строит их; только с правами статистики не видит раздел; вызовы HTTP без `reports` возвращают отказ, в том числе экспорт и сохранённые файлы.

### 2. Данные и экран конструктора

- Реализовать независимый серверный сервис отчётов и репозиторий запросов. Источник расчёта — PostgreSQL на `docflow-server`; desktop использует только версионированный HTTP API через `serverclient` и Wails-сервис.
- Добавить для каждого шаблона агрегаты и единый расчёт итогов для экрана, Excel и PDF. Исключить удвоение поручений из-за JOIN с соисполнителями и документов из-за нескольких корреспондентов. Проверить планы запросов и добавить индексы только по подтверждённой необходимости.
- Перенести уже существующие таблицы «Отчёт за период» из вкладок статистики после достижения функционального паритета в новом разделе. Проследить их цепочку от React до SQL и удалить устаревшие вызовы, DTO, Wails-методы и тестовые заглушки, если внешние потребители старого HTTP-контракта не подтверждены; при наличии таких потребителей зафиксировать срок поддержки и адаптер на общем расчёте.
- Сделать страницу с выбором шаблона, периода, допустимых фильтров, шага динамики, таблицей, итогами и графиком для динамики. Отображать пустые результаты и применённые определения. Текущие графики статистики и dashboard не переносить до появления нового раздела.
- Приёмка: одинаковые параметры дают одинаковые данные и итоги независимо от формата; тесты на границы периода, пустые выборки, несколько организаций у документа, статусы и сроки поручений. SQL и миграции проверить в изолированной интеграционной БД.

### 3. Экспорт Excel/PDF

- Генерировать оба формата на сервере из одного нормализованного результата с заголовком, параметрами, датой формирования, таблицей и итогами; для PDF предусмотреть шрифт с кириллицей, перенос строк и разбиение длинных таблиц по страницам. Excel должен содержать настоящие числовые ячейки и даты, замороженный заголовок, безопасные имена листов; текстовые значения экранировать от формул.
- Отдавать файл потоково по HTTP с корректными MIME, именем и лимитом размера. Desktop скачивает его в пользовательский каталог через безопасную запись, как вложения; путь не зависит от репозитория. Экспорт повторно проверяет `reports` и использует те же параметры и определения, что предварительный просмотр.
- Приёмка: XLSX открывается табличным редактором, PDF содержит кириллицу и читается на нескольких страницах, суммы сверены с экраном, отказ в доступе и отмена загрузки не оставляют частичный файл.

### 4. Регулярные отчёты

- Хранить шаблон расписания: владелец, тип отчёта, фильтры, периодичность (неделя/месяц), часовой пояс, формат, активность, следующий запуск. Хранить историю запусков: плановое время, параметры и версия определения, статус, ошибка, время формирования, ссылка на результат и срок хранения. Определить владельца и судьбу расписания при блокировке пользователя или отзыве `reports`.
- Запускать расписание на сервере, а не в desktop. Конкуренцию между экземплярами ограничить атомарным захватом в БД и уникальностью `(schedule_id, planned_at)`; после перезапуска безопасно обрабатывать пропущенный запуск без дублей. Файлы сохранять в серверном хранилище, предоставляя скачивание только после проверки права. Предусмотреть лимит параллельных построений, повторы и очистку по сроку хранения.
- В интерфейсе добавить создание и управление своими расписаниями, историю и ручной повтор неудачного запуска. Если требуется управление чужими расписаниями, определить отдельное административное правило до реализации.
- Приёмка: один запуск при двух экземплярах сервера, предсказуемое поведение при пропуске и смене часового пояса, запрет скачивания после отзыва права, отсутствие осиротевших файлов после сбоя и очистки.

### 5. Завершение и документация

- Обновить `docs/tech_docs.md`, README и описание прав/HTTP-контрактов; проверить ссылки. Обновить Wails bindings штатной сборкой после добавления экспортируемых методов.
- Проверить end-to-end цепочку: выбор → расчёт → экспорт → сохранение → регулярный запуск → скачивание → отзыв права. Сверить расхождения с существующей статистикой и задокументировать разные определения там, где они сохраняются намеренно.

## Решения, от которых зависит объём

- Способ доставки регулярных отчётов: хранение и скачивание в разделе или также email. В проекте не найден готовый почтовый канал; email потребует настройки отправителя, адресатов, повторов и контроля доступа к вложениям.
- Нужна ли юридически оформленная форма PDF: фирменный бланк, подпись, утверждение или фиксированный макет. Базовый PDF здесь означает читаемую выгрузку с реквизитами формирования.
- Ретроспектива подразделений: группировка по текущему подразделению исполнителя проще, но меняет прошлые цифры; группировка по подразделению на дату назначения требует сохранять снимок или события перемещения.
- Сохранение «официального» результата: неизменяемый файл и параметры запуска рекомендуются для регулярных отчётов, если исторические цифры должны воспроизводиться после изменения исходных данных.
