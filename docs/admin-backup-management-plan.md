# План восстановления и удаления копий через админпанель

Статус: запланировано, реализация не начата. Дата: 10 сентября 2026 года.

Этот план заменяет решения об отдельной recovery-панели и CLI восстановления в
[первоначальном плане](server-backup-implementation-plan.md).

## Целевое поведение

- Администратор в обычном приложении видит копии на SMB, создаёт, восстанавливает
  и удаляет их. Настройки SMB и расписание остаются в той же вкладке.
- При неисправной БД оператор сбрасывает целевое окружение, инициализирует приложение,
  создаёт администратора, настраивает SMB и выбирает копию в панели. Полный сброс
  затрагивает и БД, и файлы: оставшиеся объекты SeaweedFS нельзя смешивать с архивом.
- Восстановление заменяет текущие документы, файлы, пользователей и права данными
  копии. Оно доступно и после первичной инициализации, и для рабочего приложения.
- Отдельной recovery веб-панели, порта и постоянного аварийного ключа больше нет.
  Ключ шифрования сохранённого SMB-пароля остаётся необходимым.
- CLI `docflow-server restore` удаляется. Восстановление доступно только через
  обычную админпанель; внутренний Go-модуль восстановления сохраняется.
  Служебные команды `storage` не относятся к CLI восстановления и остаются.

## 1. Каталог копий и контракты

- [ ] Разделить историю локальных заданий и фактический каталог SMB. После сброса
  БД копии должны обнаруживаться без прежней истории заданий.
- [ ] Для копии показывать ID, дату, размер и состояние проверки. Наличие manifest
  не выдавать за успешную полную проверку архива; отмечать отсутствующие файлы.
- [ ] Добавить admin API каталога, запуска проверки/восстановления/удаления и статуса
  задания. Долгие операции возвращают job ID и продолжаются без открытого HTTP-запроса.
- [ ] Идентификаторы разрешать на сервере относительно сохранённого SMB-направления;
  не принимать произвольные пути удаления от desktop.
- [ ] Каталог поддерживает восстановление v3 и старых v2 с исходным sidecar manifest
  на SMB. Для v2 проверять имя, размер и checksum по старому контракту; локальный
  архив для восстановления предварительно размещается оператором на SMB.
  Ручное удаление в первой версии доступно для v3; для v2 показывать ограничение.

## 2. Серверное восстановление

- [ ] Разделить текущий Restore на проверку комплекта, восстановление в пустую цель
  и координатор замены текущих данных. Внутренний вызов из сервера не должен повторно
  захватывать удерживаемый сервером lifetime lease. Защиту от второй серверной
  инстанции сохранить независимо от удаления CLI.
- [ ] До изменения данных скачать архив на постоянный staging, проверить SHA-256,
  безопасную распаковку, лимиты места, dump и совместимость версии схемы. Зафиксировать
  ID и параметры задания: смена настроек SMB не меняет уже выбранный источник.
- [ ] Требовать явного подтверждения замены с датой/ID копии. Авторизовать запуск
  текущим администратором; записать инициатора в устойчивый локальный журнал.
- [ ] Сериализовать backup, restore, миграции и удаление; перевести обычные запросы
  в обслуживание, дождаться запросов и всех фоновых записей.
- [ ] Перед заменой создать и проверить локальную страховочную копию текущего
  состояния, включая пользователей и настройки. При её ошибке или недостатке места
  не начинать замену. Архив источника и страховочную копию не удалять при сбое.
- [ ] В первой версии выполнять замену в текущих выделенных БД и bucket при полном
  обслуживании. Удалять только ресурсы Docflow в сконфигурированной цели; общие БД
  и bucket с чужими данными не поддерживать. Не обещать атомарность PostgreSQL и S3.
- [ ] Восстановить dump и объекты, проверить связи вложений и checksum, учесть pending
  delete/outbox. Для поддерживаемых старых схем выполнить необходимые миграции до
  открытия обычного API. Пересоздать DB-пулы, сервисы, кэши и фоновые процессы.
- [ ] Зафиксировать фазу до каждого необратимого шага. При ошибке после начала замены
  попытаться восстановить страховочную копию; при ошибке отката оставить обслуживание
  и устойчивый маркер. После перезапуска незавершённая замена не открывает бизнес-API.
  Выход при неуспешном откате: повторный сброс целевого окружения, инициализация
  приложения и восстановление через админпанель. Исходную копию на SMB сохранять.
- [ ] После успеха отозвать все сессии, выключить расписание и очистить восстановленный
  SMB-пароль: ключ может отличаться от исходного. Администратор входит учётной записью
  из архива, заново сохраняет доступ к NAS и явно включает расписание.

## 3. Авторизация и наблюдение во время замены

- [ ] Обычная авторизация из БД не может обслуживать polling во время её замены.
  После разрешённого запуска выдать краткоживущий случайный токен только для чтения
  статуса данного задания, хранить его хеш вне заменяемой БД. Он не разрешает запуск,
  удаление, повтор или доступ к данным и не заменяет аварийный ключ новым постоянным.
- [ ] Ограничить срок действия, хранить токен в памяти клиента, исключить URL и логи.
  Для перезапуска сервера сохранить хеш и срок в защищённом локальном журнале.
- [ ] После закрытия клиента/истечения токена не открывать статус анонимно. После
  успешного завершения можно войти заново; при неуспешном откате доступен технический
  журнал и описанная процедура сброса. Не создавать второй recovery-интерфейс.
- [ ] Разрешать отмену на этапе скачивания/проверки; после начала замены отмену из UI
  запрещать. Закрытие окна не прерывает серверное задание.

## 4. Удаление копий

- [ ] Добавить подтверждаемое удаление выбранной удалённой v3-копии с датой и размером.
  История задания сохраняется и получает отметку об удалении; локальный staged-архив
  не удаляется этой операцией.
- [ ] Использовать общий SMB lock с restore и retention, повторно проверять manifest
  под блокировкой. Копию, занятую проверкой/восстановлением, удалять нельзя.
- [ ] Сохранять установленный минимум исправных копий и для ручного удаления. При
  отказе показывать причину; администратор может изменить минимум в настройках,
  но последнюю проверенную копию через панель не удалять.
- [ ] Удалять только архив и manifest выбранного комплекта. Фиксировать незавершённое
  удаление, поддержать идемпотентный повтор после ошибки SMB и перезапуска. Частичный
  результат не показывать как исправную копию и не скрывать как полный успех.
- [ ] Аудитировать инициатора, ID, результат и ошибку без паролей. Общий механизм
  блокировок и удаления использовать также для автоматического retention.

## 5. Интерфейс и удаление старой панели

- [ ] Вкладка «Резервные копии»: настройки, каталог SMB с действиями «Проверить»,
  «Восстановить», «Удалить», отдельно история заданий. Обновление каталога вручную
  и после операций; понятное состояние недоступности NAS.
- [ ] Мастер восстановления: выбор → проверка → подтверждение замены → состояние →
  результат и повторный вход. До запуска объяснить, что потребуются пароль пользователя
  из копии и повторная настройка SMB; поддержать ошибки и неуспешный откат.
- [ ] Обновить typed serverclient, desktop facade, модели и сгенерировать Wails bindings
  через `make wails-bindings`. Desktop не подключается к БД/S3/SMB напрямую.
- [ ] Удалить HTTP recovery, встроенный HTML, команду `recovery`, Compose-сервис/профиль,
  публикацию порта и DOCFLOW_RECOVERY_SECRET_FILE/PATH, а также команду
  `docflow-server restore` и её диспетчеризацию. Внутренний модуль и защитный маркер
  незавершённого восстановления сохранить; убрать рекомендации CLI из документации.
- [ ] Обновить документацию и примеры. Тестовый Samba и smoke Compose сохранить;
  убрать только части аварийной панели. Файл settings_key и staging volume сохранить.

## 6. Проверки и приёмка

- [ ] Unit/API: права, токен статуса и его истечение, подтверждение привязано к копии,
  конфликт операций, отмена до замены, допустимые пути, повтор удаления.
- [ ] Интеграционные: новый администратор после сброса обнаруживает старую копию на SMB
  и восстанавливает документы/вложения/пользователей из обычной панели.
- [ ] Проверить замену непустого окружения: лишние старые данные отсутствуют, настройки
  расписания отключены, сессии отозваны, чтение восстановленных вложений успешно.
- [ ] Проверить повреждённый архив, старую/новую схему, недоступный SMB, нехватку места,
  сбой pg_restore и загрузки объектов, рестарт на фазах замены и неуспешный откат.
- [ ] Проверить удаление, последний исправный комплект, конфликт с restore/retention,
  отсутствие локальной истории после сброса и частичное удаление на NAS.
- [ ] Заменить smoke-сценарии recovery-панели и CLI на восстановление v2/v3 через
  административный API и UI. Проверить, что удалённые команды завершаются ошибкой
  неизвестной команды без изменения БД/S3.
  Выполнить Go tests/vet, integration-test, frontend lint/test/build, docs-links-check.

Порядок реализации: каталог и контракты → координатор восстановления и устойчивый
журнал → удаление → UI → сквозные проверки → удаление recovery-панели/CLI и обновление
инструкций. Удалять существующий интерфейс восстановления после проверки замены.
