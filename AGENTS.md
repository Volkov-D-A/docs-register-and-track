# Правила работы в Docflow

## Архитектура

- Docflow — приложение для регистрации и отслеживания документов: desktop на Go/Wails v2, frontend на React, TypeScript, Ant Design и Vite.
- `docflow-server` отвечает за бизнес-операции, аутентификацию, PostgreSQL, SeaweedFS, миграции и обработку transactional outbox. Desktop обращается к версионированному HTTP API; не добавляйте в него прямые подключения к БД и объектному хранилищу.
- Подробности архитектуры и настройки находятся в [README.md](README.md) и [docs/tech_docs.md](docs/tech_docs.md). Версии зависимостей и команды сверяйте с `go.mod`, `frontend/package.json` и `Makefile`.

## Окружение и запуск

- При работе внутри WSL используйте bash и Linux-пути. Для задач на стороне Windows используйте соответствующие инструменты и пути. Код приложения должен учитывать поддержку Linux и Windows; не привязывайте пользовательские файлы к каталогу репозитория или абсолютным путям разработчика.
- Сохраняйте bash-скрипты, Dockerfile и конфигурационные файлы с окончаниями строк LF.
- Предпочитайте цели корневого `Makefile`: `make dev`, `make build-linux`, `make build-windows`. При ручном запуске Wails на Ubuntu 24.04 используйте тег `webkit2_41`, как в Makefile.
- Frontend использует npm: запускайте команды через цели Makefile либо из `frontend`. После изменения зависимостей Go выполняйте `go mod tidy` и проверяйте изменения `go.mod` и `go.sum`.
- Используйте `docker compose` (V2). Локальный стек запускается через `make storage-up`, останавливается с сохранением данных через `make storage-down`.
- Адреса и порты сервисов определяйте по конфигурации соответствующего окружения. Не предполагайте доступность PostgreSQL на `localhost:5432`. Выполняйте SQL неинтерактивно; для интеграционных тестов используйте отдельный стек из `docker-compose.integration.yaml`.
- Для долгоживущих процессов используйте управляемые сессии инструментов; для Compose — detached mode (`-d`). Сохраняйте возможность прочитать логи и остановить запущенный процесс.

## Проверки изменений

- Выбирайте проверки по затронутой области. Для Go доступны `make go-test` и `make go-vet`; для frontend — `make frontend-lint`, `make frontend-test`, `make frontend-build`. Для узких изменений допустимы прицельные проверки пакета или теста.
- Изменения SQL, репозиториев и поведения БД проверяйте через `make integration-test`: цель запускает изолированную БД и удаляет её тестовый том после завершения.
- При изменении экспортируемого API Wails обновляйте bindings через `make wails-bindings` и проверяйте полученный diff. Генерируемые bindings не редактируйте вручную.
- Для изменений ссылок в документации используйте `make docs-links-check`. Для подготовки релиза используйте `make release-gate` и проверки окружения из README.
- Добавляйте тесты, которые проверяют изменённое поведение и предотвращают регрессию. После успешных проверок расширяйте или повторяйте их только при новых изменениях, сбоях или оставшихся сомнениях.

## Выполнение задач

- В рамках запроса самостоятельно принимайте обратимые технические решения и доводите работу до проверяемого результата. Уточняйте требования, если ответ существенно меняет результат или без него нельзя безопасно продолжить.
- Учитывайте новые указания пользователя, сохраняя уже выполненную полезную работу и исходную цель, пока пользователь её не изменил.
- Отвечайте кратко по-русски: что изменено, как проверено, какие ограничения остались. Явно сообщайте о проверках, которые не удалось выполнить.
